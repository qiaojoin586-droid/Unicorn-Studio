## 1. 升级背景与目标

### 1.1 背景

当前网站处于**"能展示、难运营"**的状态，直接制约工作室的业务发展：

1. **AI 助手在生产环境完全不可用**——这是网站的招牌功能，但部署后即失效（详见 §2.2）；
2. **内容无法自主维护**——作品、学习资料全部硬编码在前端代码或手工改 SQL，改一次内容要找一次程序员；
3. **仓库卫生问题妨碍协作**——构建产物、数据库文件、密钥配置混入 git，3252 个非源码文件被跟踪，`git status` 甚至会因文件锁报错；
4. **无商业化闭环**——作品无详情页、无联系表单、无信任要素（客户/评价/备案），无法形成"展示 → 信任 → 咨询"的转化路径。

本次升级以**专业工作室网站标准**为基准，先修复致命缺陷，再补齐内容运营与转化能力，为后续上线《后台管理设计方案》铺路。

### 1.2 目标

- **可用**：AI 助手真流式、生产环境可用；数据不再被启动脚本清空；
- **可运营**：内容后台化维护（作品/新闻/轮播/留言），无需程序员介入；
- **可信**：作品详情与案例背书、联系表单、ICP 备案等信任要素齐备；
- **可部署**：MySQL + Docker + CI + 备份回滚，上线可回退；
- **可度量**：访问统计埋点 + 性能达标（Lighthouse ≥ 80）。

### 2.2 现状架构与数据流（核心发现）

```
开发模式:  浏览器 → Vite dev server (5173) → /api 代理 → Java 后端 (8080) ✅
生产模式:  浏览器 → Node 静态服务 (3000)   → /api 仅实现 health + learning/resources（mock）
                                           → /api/ai/chat 返回 404 ❌
```

**关键结论**：
1. 开发模式下前端能到达 Java 后端，但**生产模式下 Java 后端完全不被使用**——学习资料来自 Node 内置 mock 数据（`frontend/server/learningResources.js`），AI 聊天端点不存在，**AI 助手在生产环境 100% 不可用**（`frontend/server/index.js` 的 `handleApi` 函数只实现了两个 API）。

## 4. P0 问题详述与修复要点

### 4.1 P0-1 生产环境 AI 聊天完全不可用

**根因**：`frontend/server/index.js` 的 `handleApi` 只实现 `/api/health` 与 `/api/learning/resources`，`/api/ai/chat` 返回 404；`useAiChat.js` 的 `streamChat` 收到非 2xx 直接抛"AI 服务暂不可用"。Java 后端在部署架构中被架空。

**修复要点**：
1. 明确统一架构：**Node 静态服务只做静态托管 + `/api/*` 反向代理到 Java 后端**（Java 后端是唯一业务源）。删除 `frontend/server/learningResources.js` mock 数据（开发环境 Vite 已代理到 8080，mock 只会制造"集成断裂不可见"的假象）。
2. Node 端新增代理，**透传 SSE 且禁用缓冲**。最小可用骨架：

```js
// server/index.js 新增：/api/** 反向代理（SSE 透传）
const TARGET = process.env.API_PROXY_TARGET || 'http://127.0.0.1:8080'

function proxyToBackend(req, res, pathname) {
  const upstream = http.request(TARGET + pathname, {
    method: req.method,
    headers: { ...req.headers, host: new URL(TARGET).host },
  }, (upRes) => {
    res.writeHead(upRes.statusCode, {
      ...upRes.headers,
      'Cache-Control': 'no-store',   // SSE 响应不缓存
    })
    upRes.pipe(res)                  // 关键：流式 pipe，不做任何聚合缓冲
  })
  upstream.on('error', () => sendJson(res, 502, { code: 50200, message: '后端服务暂不可用' }))
  // 注意：透传时不重算 Content-Length，直接复用原始 header；若缺失则删除该头，由 Node 自行处理
  req.pipe(upstream)                 // 请求体透传（POST 聊天消息）
}
// handleApi 中：本地实现的接口照旧，其余 /api/* 一律 proxyToBackend
```

3. `smoke-test.js` 增加 `/api/ai/chat` 用例（POST + 验证收到 `data:` 帧）——本次唯一坏掉的功能恰好没被测到，测试清单需与真实端点同步。

**验证**：`npm run build && npm start` 后打开 AI 助手对话，能收到流式回复；smoke-test 全绿。

### 4.2 P0-2 假流式与线程模型

**根因**：
- `AiChatService.java:55` 调用非流式接口（请求体无 `"stream": true`），整个生成期间线程阻塞；
- 拿到全文后按 10 字符 + `Thread.sleep(50)` 切片伪装流式（:64-69）；
- `SseEmitter` 超时仅 60s（`AiChatController.java:25`），超过则静默 complete → 用户收到空回复；
- `CompletableFuture.runAsync` 落在公共 ForkJoinPool（:27），并发时阻塞 IO + sleep 占满池子；
- `RestTemplate` 默认构造无任何 connect/read 超时（`AiChatService.java:26`），连接挂死即线程泄漏。

**修复要点**：
1. 改用**真流式**。首选引入 Spring AI（`ChatClient.stream()` 直接返回 `Flux<String>`，与 SseEmitter 天然契合）；备选：`WebClient`（`spring-boot-starter-webflux`）请求 `"stream": true` 并逐 delta 转发。请求参数中 `max_tokens` 按模型限额配置化。
   - **选型兼容性说明**：Spring AI 1.0.x（GA）官方支持 Spring Boot 3.3，引入时需在 pom 添加 Spring AI BOM 并核对与 Boot 3.3.5 的版本矩阵；DeepSeek、通义千问、Moonshot 等国内厂商均提供 OpenAI 兼容端点，只需改 `base-url` 与 `model` 配置即可切换，与现有 `app.ai.api-url/model` 配置思路一致，无供应商锁定；若不愿引入新依赖，手写 WebClient SSE 解析约 100 行，但需自行处理错误帧与断连。
2. 配置超时：connect 5s / read 120s（Spring AI 下配 `spring.ai.openai.chat.options.*`；WebClient 下配 HttpClient）。
3. 专用线程池：声明 `@Bean("aiExecutor") ThreadPoolTaskExecutor`（如 core 2 / max 8 / 队列 50 + 拒绝策略），SSE 任务显式提交到该池，**禁止使用公共池**。
4. 客户端断开即取消：`emitter` send 抛 IOException / `onCompletion` / `onTimeout` 时取消 Future 与底层 Flux 订阅，停止计费消耗。
5. 删除所有 `Thread.sleep` 伪装逻辑与 mock 兜底（mock 移入 dev profile，见 4.3）。

**验证**：配真实 key 后首个 token 延迟 < 2s；模拟慢生成（>60s）仍能持续输出；并发 20 请求无饥饿。

### 4.3 P0-3 LLM 错误处理

**根因**：`AiChatService.java:57-73` 逐层判空后静默跳过（401/429/错误体 → 用户收到空白"回答"，HTTP 恒 200）；`:78` 把 `e.getMessage()` 作为聊天内容分片发给用户（泄漏内部细节，且含换行时会破坏 SSE 帧）；`:34-37` 未配 API key 时生产环境静默输出固定假话，无任何日志。

**修复要点**：
1. **错误走错误通道**：流式开始前的错误（参数校验、上游 4xx/5xx、超时）通过 HTTP 错误状态 + 统一错误 JSON 返回；流开始后的中断通过**命名 SSE 事件**（`event: error` + JSON payload）通知前端，前端按事件类型渲染"AI 服务暂时不可用，请稍后重试"，**绝不透传 `e.getMessage()`**。
2. 完整错误日志：`log.error("AI 调用失败", e)` 记录状态码与响应体（脱敏），供排查。
3. mock 兜底仅限 dev profile：`@Profile("dev")` 或配置开关，生产未配 key 时**直接返回 503** 并在启动日志告警"AI_API_KEY 未配置"。
4. 前端配合：`streamChat` 解析 `event:` 字段；空流（无任何 chunk 即结束）时回退显示友好错误气泡，不静默丢弃。

**验证**：无 key 启动生产 profile → AI 对话返回明确错误；用错误 key 调用 → 日志有完整记录、用户只看到通用提示；前端无 "undefined" 或异常堆栈出现。

**验证**：`git status` 不再报 Permission denied；clone 仓库后文件数大幅下降；构建后 `git status` 干净。

### 4.5 P0-5 前端 SSE 解析缺陷

**根因**：`streamChat` 对每个 chunk 直接 `split('\n')`，TCP 分包把一行拆两段时前半段被当作完整行、后半段因不满足 `startsWith('data: ')` 被丢弃 → 回答随机丢字；`[DONE]` 只 break 内层 for，外层 `while(true)` 继续 read → 服务端 keep-alive 时 loading 永远卡死；全程无 AbortController，关闭对话框/切路由后请求继续写 store。

**修复要点**：
1. **跨 chunk 行缓冲**：维护 `buffer` 字符串，`buffer += decoder.decode(value, {stream:true})`，按 `\n` 切出完整行处理，残留片段留待下一 chunk 拼接；流结束时 `decoder.decode()` 收尾 flush。
2. `[DONE]` 直接 `return` 退出整个读取循环。
3. `AbortController`：`useAiChat` 持有 controller，`AiChatDialog` `onUnmounted`（及路由切换）时 `abort()`；`finally` 中兜底复位 loading/avatarState（防悬挂状态）。
4. 解析 `event: error` 命名事件（配合 4.3）；空回复回退友好错误。
5. 顺带修复 `useApi.js` headers 合并顺序（先 `...options` 再合并默认 headers）与统一错误形状。

**验证**：手写单测模拟 `data: 你` / `好\n` 分片边界用例（Vitest）；实际对话长回答无丢字；对话中途关闭对话框，Network 面板请求被取消，重开后状态正常。

### 4.6 P0-6 IME 回车误发送

**根因**：`ChatInput.vue` 的 `handleSubmit` 未检查输入法组合态。

**修复**：`handleSubmit` 首行加 `if (event.isComposing || event.keyCode === 229) return`。

**验证**：中文拼音输入选词按 Enter 仅确认候选词，不发送消息。

## 9. 回滚与备份策略

### 9.1 代码与版本回滚

- **里程碑打 tag**：每个阶段完成验收后打 `upgrade-p1` … `upgrade-p4` 标签，回滚即 `git checkout <tag>` + 重新部署对应产物；
- **前端双版本目录**：部署时保留上一版 `release-YYYYMMDD-HHmm/`，nginx 用**符号链接切换**（`ln -sfn release-新 release-current`），回滚 = 换回旧链接 + `nginx -s reload`，秒级完成；
- **后端**：Docker 镜像按版本 tag 保存（`:latest` 与 `:<git-sha>` 双 tag），回滚 = 启动上一 sha 镜像；
- **部署变更一律可逆**：nginx 配置文件纳入 git 并保留上一版副本。

### 9.2 数据备份与回滚

**H2→MySQL 迁移（阶段四 4.2）**：

1. **迁移前**：① 复制 H2 数据文件备份（`unicorn_studio.mv.db` → 带日期文件名）；② 停止写入后执行 mysqldump 导出（若 H2 期间已用）；③ 导出 H2 数据为 SQL/CSV 快照；
2. **迁移中**：Flyway 建表 → 数据导入脚本（学习资源等少量数据手工 INSERT 即可）；
3. **迁移后校验**：行数对比（H2 vs MySQL 各表 count 一致）+ 抽查记录内容一致；
4. **观察期**：新库并行运行 3 天，旧 H2 文件保留 30 天后归档删除；
5. **回滚路径**：MySQL 出问题 → 切回 H2 配置（`spring.datasource` 还原 + 重启）。若观察期内 MySQL 已有新写入：先按 `created_at` 导出增量（mysqldump `--where`）→ 切回 H2 → 补入增量数据；**更稳妥做法：观察期 3 天内站点设为只读/暂停写入**（工作室站点写入场景少，可接受）。

**Flyway 原则**：迁移脚本只增不改；破坏性变更（改列/删表）必须新建 V-next 脚本并配套**备份点**（执行前自动 mysqldump 一次）；Flyway 不提供 undo，回退 = 备份恢复（流程写入运维手册）。

### 9.3 各阶段回滚操作

| 阶段 | 回滚方式 | 数据风险 |
|---|---|---|
| 阶段一 | 前端切回旧 release 目录；后端回滚 jar 镜像 | 无（不涉及数据变更） |
| 阶段二 | 同上 + data.sql/异常处理器为代码变更，回滚即恢复旧行为 | 低（data.sql 幂等改造只影响启动种子逻辑） |
| 阶段三 | 同上 + 新增表不删除（Flyway 版本不回退，新表空置无影响） | 低（新增表为主，无破坏性变更） |
| 阶段四 | MySQL 出问题 → 按 9.2 切回 H2；nginx/Docker 按 9.1 切换 | 高（见 9.2 迁移备份流程） |

### 9.4 演练要求

- 每个阶段上线前在**测试环境**完整走一遍"上线 → 发现严重问题 → 回滚"流程，记录耗时；
- 阶段四正式上线前必须完成一次 MySQL 数据迁移演练 + 备份恢复演练（用演练数据恢复一次）。
