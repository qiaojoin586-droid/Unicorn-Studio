## 1. 需求与结论

**需求**：后台「审计日志」与「SQL 监控」数据仅保留最近七天。需设计并实现定期删除策略——自动清理
超过保留期的审计日志、SQL 监控数据，以及**这些清理操作自身产生的日志**；保留期限默认 7 天，
且在后台可配置为 **7 / 15 / 30 / 90** 天；需明确执行周期、触发方式、配置项的存储与生效逻辑、
以及删除操作的安全性与可恢复性。

**核心结论**：

1. 「SQL 监控数据」**不在数据库里**——它是 Druid 连接池的 JVM 内存聚合统计
   （`DruidStatManagerFacade`，重启清零），**没有表、没有逐条时间戳**，因此**无法按记录裁剪**；
   等价实现为「距上次重置满 N 天则整体 `resetAll()`」，使统计窗口不超过保留期。
2. 保留期限复用 `site_settings` 的 `retention` 分组存储（与 V12/V13 同一范式，**不新建表**），
   每次清理实时读库 ⇒ **改配置无需重启即生效**。
3. 「清理自身产生的日志」被闭环处理：清理任务本身是 `@AuditLog` 写接口，其数据库审计行会在
   下一轮按同一规则删除；其管理端审计**文件**由本任务按同一保留期裁剪日期目录。

## 2. 清理对象界定

| # | 对象 | 物理载体 | 是否含时间戳 | 清理方式 |
|---|---|---|---|---|
| 1 | 审计日志 | MySQL 表 `sys_operation_log.created_at` | ✅ 有（已有索引 `idx_operation_log_time`） | 按 `created_at < cutoff` **分批物理删除** |
| 2 | SQL 监控数据 | Druid JVM 内存聚合（无表） | ❌ 无逐条时间戳 | 距上次重置满 N 天 → `resetAll()` 整体重置 |
| 3 | 清理操作自身的日志 | ① `sys_operation_log` 中本任务产生的行<br>② `logs/admin/yyyy-MM-dd/app-admin.log` | ① 有<br>② 目录名含日期 | ① 下一轮同规则删除；② 按保留期裁剪整个日期目录 |

> **关于对象 2 的判定依据**：`SqlMonitorController` 直接读取 `DruidStatManagerFacade.getInstance()`，
> `reset` 走 `statManager.resetAll()`；全库无 SQL 监控表。此点曾易被误解为「库表数据」，特此记录。

> **关于对象 3 的闭环**：这是需求中「清理日志同样按保留期定期删除」的落点——若不做②，
> 清理任务每天写一行审计，会自我堆积到 logback 的 30 天上限；做②后与保留期一致。

## 3. 执行周期与触发方式

| 触发方式 | 说明 |
|---|---|
| **定时任务**（主） | `@Scheduled(cron = "${app.retention.cron:0 30 3 * * *}")`，默认**每日 03:30**。刻意错开既有定时任务：01:00 埋点聚合、02:00 数据备份、03:00 统计聚合。 |
| **后台手动**（辅） | `POST /api/admin/retention/cleanup`，支持 `dryRun`（预览）与 `resetSqlMonitor`（强制重置统计）。先预览再执行，界面内置二次确认。 |

**开关语义**：`retention.enabled=false` 时，**定时分支直接跳过**（不删任何数据）；
**手动分支不受开关限制**——管理员显式操作优先，保证关闭自动清理后仍可应急清理。

## 4. 配置项的存储与生效逻辑

### 4.1 存储（`site_settings` 表，分组 `retention`）

| setting_key | 含义 | 默认 | 写入方 |
|---|---|---|---|
| `retention.days` | 保留天数，**仅允许 7/15/30/90** | `7` | 后台页面 |
| `retention.enabled` | 是否启用定时自动清理 | `true` | 后台页面 |
| `retention.sql_monitor_last_reset` | 上次 SQL 监控重置时间（重置节流的基准） | 空 | 系统运行时 |
| `retention.last_run_at` | 上次清理执行时间 | 空 | 系统运行时 |
| `retention.last_run_trigger` | 上次触发方式（scheduled/manual） | 空 | 系统运行时 |
| `retention.last_run_deleted` | 上次删除的审计日志条数 | 空 | 系统运行时 |

运行时键落库的意义：**重启后仍可观测**「上次何时清理、删了多少」，否则只存在于内存。

### 4.2 部署级参数（`application.yml`，不入库）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `app.retention.cron` | `0 30 3 * * *` | 执行周期。环境变量 `RETENTION_CRON` 可覆盖 |
| `app.retention.max-delete-per-run` | `50000` | 单轮最多删除行数，防首次接入时一次性删空历史数据 |

> **为何周期不入库**：执行周期属部署策略（与 `app.backup.cron` 同层），改它影响运维排期，
> 不宜由业务后台随意变更；需求只要求**保留期限**可配。

### 4.3 生效逻辑

```
每次执行 → loadConfig() 实时读 site_settings → normalizeDays() 兜底 → 计算 cutoff = now - days
```

- **无需重启**：配置在每次执行时重新读取，保存后立即作用于下一次执行。
- **非法值处理**：后台保存时非 7/15/30/90 → **400 报错**（不做静默兜底，避免管理员误以为已生效）；
  读取时若库中存在非法值（如手工改库）→ 静默回落默认 7 天，保证任务不会因脏配置中断。

## 5. 清理算法与安全设计

```
cutoff = now - days
1) 审计日志：循环 DELETE FROM sys_operation_log WHERE created_at < cutoff LIMIT min(2000, 剩余配额)
   → 直到返回 0 行，或达 max-delete-per-run（标记 capped，剩余留待下轮）
2) SQL 监控：若 forceSqlMonitor || (now - last_reset) >= days → resetAll() 并回写 last_reset
3) 审计文件：裁剪 logs/admin/ 下日期早于 cutoff 日期 的整个 yyyy-MM-dd 目录
4) 回写执行摘要（last_run_at / _trigger / _deleted）
```

| 安全设计 | 目的 |
|---|---|
| **单批 `LIMIT 2000`** | 避免一条大 DELETE 造成长事务、大范围行锁、主从复制延迟 |
| **单轮上限 `max-delete-per-run`** | 首次接入时历史数据可能很多，分批跨轮消化，避免一次打满 IO |
| **dry-run 预览** | `GET /preview` 与 `POST /cleanup?dryRun=true` 只统计不写；界面默认先预览 |
| **批量二次确认** | 「立即执行清理」弹窗展示将删除的条数与截止时间后才执行 |
| **目录名正则 + 路径前缀双保险** | 仅处理严格匹配 `\d{4}-\d{2}-\d{2}` 的目录，且解析后的绝对路径必须仍在 `logs/admin` 之下 |
| **目录跨平台无关文件删除** | 只删日期目录，不触碰 info/warn/error 等其它日志目录 |
| **定时任务自兜异常** | `try/catch` 包裹，避免调度线程持续打印堆栈 |
| **写入失败不中断** | 观测键回写失败仅告警，不影响已完成的删除结果 |

## 6. 安全性与可恢复性

**删除性质**：审计日志为**物理删除**（`DELETE`），**无法从数据库自身回滚**。

**可恢复性依赖链**：

1. **每日数据库备份**（既有能力，见《后台管理实施方案》§5.6）：`mysqldump` 每日 02:00 全量备份，
   默认保留最近 7 份。被清理的审计行只要还在某份备份的时点内即可恢复。
   > ⚠️ **运维建议：保留期不应短于备份保留份数**——默认「保留 7 天 + 备份 7 份」是对齐的；
   > 若保留期调小到小于备份份数，则数据虽有备份但备份本身也保留更久，需自行评估合规口径。
2. **预览与上限**：见 §5，给管理员在执行前判断影响范围的机会。
3. **降低误删面的设计**：只删 `sys_operation_log`（不涉及业务数据表）；SQL 监控仅重置内存统计，
   不涉及任何持久化数据。

**局限性（如实说明）**：审计**文件**受 logback `maxHistory=30` 硬上限约束，
故保留期设为 90 天时文件侧实际仍为 30 天；数据库中的审计日志不受此限制。
若需二者完全一致，需将 logback 的 `maxHistory` 也接入配置（当前未做，见 §10）。

## 7. 接口与权限

| 方法 | 路径 | 权限码 | 说明 |
|---|---|---|---|
| GET | `/api/admin/retention` | `retention:view` | 状态总览（配置 + 上次执行 + 下次执行时间 + 上次统计重置时间） |
| GET | `/api/admin/retention/preview` | `retention:view` | 预览（无副作用） |
| PUT | `/api/admin/retention` | `retention:edit` | 保存保留期限与开关 |
| POST | `/api/admin/retention/cleanup` | `retention:run` | 立即清理（`?dryRun=&resetSqlMonitor=`） |

- 权限码 `sort_order` 为 108/109/110，`module='数据保留'`，`type` 分别为 MENU/BUTTON/BUTTON。
- **权限不下发给 EDITOR**：数据保留属系统级破坏性操作，仅 `SUPER_ADMIN`（代码内加载全量权限）可用。
- 保存与清理均为 `@AuditLog` 写接口（`module="数据保留"`），执行留痕进入审计日志——
  而审计日志本身又受本保留期约束，形成闭环。

## 8. 后台界面

新增 `admin/src/views/settings/RetentionView.vue`，路由 `/retention`，侧边栏菜单「数据保留」（图标 `Delete`），
位于「数据备份」之后。页面含四块：

1. **策略配置**：保留期限下拉（7/15/30/90 天）、自动清理开关、只读展示执行周期与单轮上限；
2. **运行状态**：当前生效保留期、下次自动执行、上次执行（时间+触发方式）、上次删除条数、SQL 监控上次重置；
3. **立即清理**：说明文案 + 「预览待清理数据」+ 「同时重置 SQL 监控统计」+ 「立即执行清理」（二次确认）；
4. **策略说明**：三类清理对象的机制说明、触发方式、logback 30 天限制、安全与可恢复性提示。

## 11. 已知限制与后续可选项

| 限制 | 说明 | 可选改进 |
|---|---|---|
| 审计文件受 logback 30 天上限 | 保留期 90 天时文件侧仍为 30 天 | 把 `maxHistory` 改为读环境变量，或改用自定义 `TriggeringPolicy` 按配置裁剪 |
| SQL 监控无逐条时间戳 | 只能整体重置，无法精确按天裁剪 | 若未来需要窗口化趋势，可落 `stats_daily` 类聚合表替代内存统计 |
| `max-delete-per-run` 未在后台暴露 | 属运维参数，需改配置重启 | 如需动态调整可并入 `retention` 分组 |
| 手动清理不受 `enabled` 限制 | 设计如此（管理员显式优先） | 若需强管控可在接口层加二次确认令牌 |
