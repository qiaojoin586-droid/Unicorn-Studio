> 排查时间：2026-09-22

> 涉及文件：`backend/src/main/java/com/unicorn/studio/admin/service/BackupService.java`
> 结论：**已定位并修复，端到端验证通过。需重启 8080 实例生效。**

## 一、摘要

| 项目 | 内容 |
|---|---|
| 现象 | 手动点击「立即备份」后记录变为 `failed`，备份文件未生成 |
| 报错 | `mysqldump 退出码 2: mysqldump: Got error: 1045: Access denied for user 'root'@'localhost' (using password: YES) when trying to connect` |
| 栈顶 | `BackupService.runMysqldump(BackupService.java:171)` ← `runBackup(BackupService.java:120)` |
| **根本原因** | **`runMysqldump` 只从 JDBC URL 中解析「库名」，从未传递 `--host`/`--port`。mysqldump 因此退回默认的 `localhost`，去连「运行后端这台机器上的 MySQL」，而不是 `spring.datasource.url` 指向的那台** |
| 触发条件 | `spring.datasource.url` 指向**远程** `39.106.191.149:3306`，而本机 3306 也跑着 MySQL 且口令不同 |
| 严重程度 | **高**。除报错外还存在一支**静默错备**路径（见 §四），会让人误以为备份正常 |
| 修复 | 显式传 `--host`/`--port`（从 JDBC URL 解析），并补 `--protocol=TCP`、`--default-character-set=utf8mb4`；凭据值加引号 |
| 验证 | 真实定时备份链路端到端通过：`status=success`、0 失败；抽验备份内容确为远程库、21 张表、未截断、无乱码 |

## 二、现象与关键报错

```
2026-09-21 20:24:24.073 [backup-1] ERROR c.u.studio.admin.service.BackupService - 备份失败 recordId=2
java.io.IOException: mysqldump 退出码 2: mysqldump: Got error: 1045:
  Access denied for user 'root'@'localhost' (using password: YES) when trying to connect
	at com.unicorn.studio.admin.service.BackupService.runMysqldump(BackupService.java:171)
	at com.unicorn.studio.admin.service.BackupService.runBackup(BackupService.java:120)
```

两条线索：

1. **`using password: YES`** —— 密码**已经被送出**，只是被服务器拒绝。所以不是「没读到密码」。
2. **`'root'@'localhost'`** —— 连接来源被认作 `localhost`。但配置里并不是 `localhost`。

第 2 条是关键：报错主机与配置主机**不一致**。

---

## 三、配置事实核对

| 配置项 | 实际值 | 说明 |
|---|---|---|
| `spring.datasource.url` | `jdbc:mysql://39.106.191.149:3306/unicorn_studio?...` | **远程**服务器 |
| `spring.datasource.username` | `${DB_USERNAME:root}` | root |
| `spring.datasource.password` | 由 `application-local.yml` 覆盖（11 位） | **只覆盖了 password**，url/username 不覆盖 |
| 后端所在机器 | 本机 | 本机 **3306 也在运行 MySQL**（口令为另一个） |

于是形成的错配是：**手上拿的是「远程库的口令」，连接目标却是「本机库」** → `1045`。

---

## 四、根本原因

`BackupService.runMysqldump()` 构建命令时是这样的：

```java
String dbName = extractDbName(jdbcUrl);          // 只取了库名
process = new ProcessBuilder(mysqldumpPath,
        "--defaults-extra-file=" + credentials,  // 凭据文件里只有 user/password
        "--single-transaction", "--routines", dbName)   // ← 没有 --host / --port
        .start();
```

`extractDbName()` 只从 URL 中截取最后一段作为库名，**host 与 port 被丢弃**。而 mysqldump 官方行为是：
**不指定 `--host` 时默认连接 `localhost`**。也就是说，备份工具连接的是「跑后端的那台机器」，
而不是「应用正在使用的那台数据库」。

### 这个缺陷有两支后果，后者比报错更危险

| 分支 | 条件 | 表现 | 可发现性 |
|---|---|---|---|
| A（本次命中） | 本机库口令 **≠** 远程库口令 | `1045 Access denied for 'root'@'localhost'`，记录 `failed` | 容易发现 |
| B（更危险） | 本机库口令 **恰巧等于** 远程库口令 | mysqldump **成功退出**，文件生成、界面显示「成功」，**但内容是本机库** | **静默错备** |

分支 B 意味着：备份列表看起来一切正常，直到真的要恢复时才发现数据不对——此时原始备份早已被
`cleanupOldBackups()` 按保留份数清理掉。因此修复原则定为 **「宁可失败，也不能错备」**：
host 必须显式指定，绝不依赖客户端默认值。

> 本项目恰好具备触发条件：`39.106.191.149` 是远程库，而本机 3306 也长期运行着 MySQL。

---

## 五、决定性证据

复现方式：**照抄 `BackupService` 拼出的 argv，仅切换 `--host`**，凭据文件内容与代码完全一致
（`[client]` + `user=root` + `password=<application-local.yml 中的值>`），库名 `unicorn_studio`。

| # | argv（省略 `--defaults-extra-file`） | 退出码 | stdout 头部 |
|---|---|---|---|
| 1 | `--single-transaction --routines unicorn_studio`（**现状**） | **2** | 空；stderr 与线上报错**逐字一致** |
| 2 | `--single-transaction --routines --host=39.106.191.149 --port=3306 unicorn_studio` | **0** | `-- Host: 39.106.191.149  Database: unicorn_studio` |
| 3 | `--single-transaction --routines unicorn_studio`（**换用本机库口令**） | **0** | `-- Host: localhost` |

三行对照构成完整闭环：

- 1 → 精确复现线上故障，且**唯一差异变量就是 `--host`**；
- 2 → 补上 `--host/--port` 后立即成功，**目标正是远程库**；
- 3 → 反证「不传 host 时命中的确实是本机库」——因为换成**本机**口令就成功了。

## 六、修复方案

仅改动 `BackupService.java` 一个文件（+80 / −1）。

### 6.1 显式指定目标服务器（核心修复）

新增 `parseHostPort(jdbcUrl)`，从 JDBC URL 解析 host/port 并传给 mysqldump，覆盖以下形态：

| URL 形态 | 解析结果 |
|---|---|
| `jdbc:mysql://host:3306/db` | `host`, `3306` |
| `jdbc:mysql://host/db`（省略端口） | `host`, `3306`（默认） |
| `jdbc:mysql://h1:3306,h2:3306/db`（多主机） | `h1`, `3306`（取第一个，与驱动一致） |
| `jdbc:mysql://[::1]:3306/db`（IPv6） | `::1`, `3306` |
| `jdbc:mysql:///db` | `localhost`, `3306`（该写法语义即本机） |

### 6.2 一并加固的参数

| 参数 | 为什么加 |
|---|---|
| `--protocol=TCP` | host 为 `localhost` 时，Windows 客户端可能改走 **named pipe**；显式 TCP 消除行为分叉。 |
| `--default-character-set=utf8mb4` | 服务器默认字符集若不是 `utf8mb4`，不加会产出**乱码备份**（本项目全库 `utf8mb4_0900_ai_ci`）。 |
| 凭据值加双引号（`quoteOptionValue`） | MySQL option file 中，**未加引号的值会在 `#` 处起注释、并裁掉首尾空白** ⇒ 口令含 `#` 或首尾空格时被**静默截断**，症状同样是「密码对却 1045」。引号内转义 `\` 与 `"`。 |

### 6.3 刻意*不*加的参数

| 参数 | 不采用的理由 |
|---|---|
| `--set-gtid-purged=OFF` | 实测该远程库**无 GTID**（dump 中无 `GTID_PURGED` / `@@GLOBAL.GTID_EXECUTED`），且该选项在 MySQL 新版本有被移除的风险，不引入无谓的兼容性隐患。 |

`--routines` 保留（实测无 `DEFINER`，可正常导出）。

## 七、验收（真实端到端）

**方法**：起临时实例 `18081/18091`（`SPRING_PROFILES_ACTIVE=local`，不动用户的 8080），
`BACKUP_CRON` 设为秒级，跑**真实备份链路**
（`trigger()` → `@Async("backupExecutor")` → `runBackup()` → `runMysqldump()`）。
该链路与「手动备份」按钮**共用同一段代码，仅 `type` 字符串不同**（`manual` / `scheduled`），故覆盖等价。

**结果**：

| 检查项 | 结果 |
|---|---|
| `backup_record` 状态 | 出现 `status=success`（修复前恒为 `failed`），**失败 0 条** |
| 备份文件 | 真实产出 `unicorn_*.sql.gz`，gzip 魔数 `1f 8b` 正确 |
| 解压后 `-- Host:` | **`39.106.191.149`** ✓ 确为远程库（修复生效的直接证据） |
| `CREATE TABLE` 数量 | **21 张** —— 与项目表数量完全一致 |
| 完整性 | 尾部含 `Dump completed on`（未被截断） |
| 字符集 | 含中文的 INSERT 行显示正常，**无乱码** |

附带一个闭环佐证：修复后的备份内容里，能看到
`INSERT INTO backup_record VALUES (2,...,'manual','failed','mysqldump 退出码...`
—— **正是本次报障的那条失败记录本身**，说明修复后的备份数据完整可用。

## 八、影响面与数据安全

### 8.1 备份文件未受影响

真实备份目录 `data/backups/` **始终未被触碰**（验证时把 `BACKUP_DIR` 指向了临时目录）：
`unicorn_20260903_020000.sql.gz`（10507 B，历史成功备份）完好。

### 8.2 一处副作用及恢复（已处理）

验证过程中，临时实例指向的是**生产库**，而 `cleanupOldBackups()` 在保留份数（`retention-count=7`）
之外会**同时删除文件与数据库记录**。高频触发后，库中**真实的 `id=1`、`id=2` 记录被裁掉**
（文件未丢）。已依据验证前留存的全库 dump 按**原值精确恢复**，并清除 7 条测试记录：

| id | type | status | file_name | file_size | created_at |
|---|---|---|---|---|---|
| 1 | scheduled | success | unicorn_20260903_020000.sql.gz | 10507 | 2026-09-03 02:00:00 |
| 2 | manual | failed | NULL | NULL | 2026-09-21 20:24:24 |

`backup_record` 表已回到测试前状态（`id=2` 的 `error_msg` 中文完整未乱码）。

> **教训**：用临时实例验证「会写库的定时任务」时，**改 `BACKUP_DIR` 只能保住文件，数据库记录照样会被裁**。
> 安全做法是使用独立的临时库，或验证前先对目标表做 `--no-create-info` 导出。

## 十、遗留与建议

| # | 事项 | 建议 |
|---|---|---|
| 1 | `data/backups/unicorn_20260921_202423.sql.gz` 仅 **20 字节**（gzip 头尾） | 是那次失败留下的空壳文件，建议删除 |
| 2 | 备份失败时仍会留下空壳 `.sql.gz` | 可考虑在 `runMysqldump` 失败分支中删除未完成的 `target`，避免目录里混入无效文件 |
| 3 | `retention-count` 默认仅 7 份 | 秒级/高频触发时会迅速裁掉历史；生产 `cron` 为每日 02:00，影响有限，如需更长历史可调大 |
| 4 | 备份未做「可恢复性」校验 | 可考虑备份完成后校验 gzip 尾部标记（`Dump completed`），把「文件生成」升级为「文件有效」 |
