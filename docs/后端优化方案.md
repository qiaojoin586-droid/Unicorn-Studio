## 1. 现状总评

后端整体质量**良好偏上**，V15/V16 两轮改造（Redis 缓存分层、AI 助手）留下了不少专业级设计：Redis 缓存的**穿透空值哨兵、TTL ±10% 抖动、熔断降级、启动异步预热**都已落地；浏览量做了**写热点剥离**（Redis INCR + 定时增量回写，不再 `SELECT` + 全列 `UPDATE`）；权限做了**跨请求(Redis 10min) + 请求内(ThreadLocal)** 两级缓存且 ThreadLocal 在 `finally` 中无条件清理；AI 对话走 `SseEmitter` + Reactor 流式，**长连接不占用 Tomcat 工作线程**；文件上传与 mysqldump 备份都是**真流式**，不吃堆；全站 **0 处 `BeanUtils.copyProperties`**（VO 一律手写静态工厂，省掉反射开销）；审计日志做了**递归字段脱敏**且把明文 API Key 列入敏感名单。

但从「能跑」到「跑得省、扛得住」之间，存在**五类系统性短板**（**安全排在第一位**，理由见下）：

0. **⚠️ 安全：存在可被利用的身份伪造与凭据泄漏（见 §9）**——前台 JWT 的签名密钥在 `PublicAuthService` 构造函数里有一个**硬编码的默认值**，且 `application.yml` **从未声明该配置项** → 按默认配置部署时，**任何读过本仓库的人都能伪造任意前台用户的 token**（评论身份伪造、绕过禁言）；`CryptoService` **未把机密性密钥与 JWT 签名密钥分离**（生产用 `ADMIN_JWT_SECRET` 派生 AES 密钥，本地开发无密钥时**明文落库**）；`application.yml` 里 **Redis 口令与主机是真实凭据/公网 IP 且已进入 git 历史**；此外 `X-Forwarded-For` 被无条件信任，**使全部 IP 维度限流可被绕过**（S-7）。这些**必须先于本文档的任何性能项修复**。
1. **线程池与调度基本没调**——`asyncExecutor`(2/8/200) 未设拒绝策略，且审计切面是在 **`finally` 块里**提交异步任务的，队列满时 `TaskRejectedException` 会**覆盖业务的正常返回值**（业务成功却返回 500）；5 个 `@Scheduled` 任务全部挤在 Spring 默认的**单线程**调度器上；Tomcat 的 200 个工作线程对着 Druid 的 **10 个连接**；Java 21 已可用但**未启用虚拟线程**；SMTP 发信还在 `@Transactional` 里同步阻塞且**没有配任何超时**（可无限挂起并占死连接）；「测试 AI 连通性」同步阻塞线程最长 120 秒。
2. **全站 `SELECT *`，把大字段读出来再丢掉**——`work` / `news` / `learning_resources` 的 `content` 是 **MEDIUMTEXT（最大 16MB）**。前台 3 个列表接口把正文全量读出、反序列化、再在 `VO.from()` 里丢弃；后台 4 个列表接口则把每页 10 份富文本**原样塞进 JSON 返回给浏览器**。全仓库只有 4 处用了列投影。
3. **分页与聚合大量在 Java 侧完成**——评论列表是**真·假分页**（全量 `selectList` 后 `subList`，页大小不影响 DB 开销，这是本类里唯一有实际用户感知的一项）；仪表盘单次请求 **14 条查询**（口径见 V15 §2.7）且其中 6 条打在只增不减的 `visit_log` 上；批量接口（改角色权限、批量审评论、保存站点配置）都是**循环内逐条查+逐条写**的 N+1。~~UV 统计把整窗口的去重 IP 哈希全拉进堆~~ —— **经实测已降级为 P2**（真实库仅 840 行、去重 IP 数为 **1**，见 B-15），**不构成系统性短板**。
4. **没有任何量化基线与运行参数**——`pom.xml` 无 actuator/micrometer，`/api/health` 无条件返回 `{"ok":true}` 不探 MySQL/Redis；全项目**无 `-Xmx` / GC / OOM dump 参数、无 Dockerfile、无启动脚本**，实际以 JVM 默认「物理内存 / 4」运行。这意味着**改动的收益无法测量**——这是本次优化必须先补的前置条件（见 B-19）。

### 优先级定义与排序规则（v1.1 新增）

**P0** = 代码今天就处于缺陷或错误状态（含未提交在制品的正确性与安全性问题）；**P1** = 显著影响吞吐/延迟/内存，或在高负载下会暴露的短板；**P2** = 打磨项，排期从容时做。

> ### ⚠️ 排序规则：安全类问题**一律优先于性能类问题**，同级内先安全后性能
>
> 本文档 v1.0 把「PV 埋点 UA 串号」（性能/数据质量）与「前台身份可伪造」（安全）**并列在 P0**，读者若按文档顺序实施，会先修前者——**这是错的**。两者的性质不同：
>
> | | 性能/正确性类（B-*） | 安全类（S-*） |
> |---|---|---|
> | 被利用的前提 | 需要高并发 / 特定时序 | **只需读到仓库，或一个普通用户** |
> | 最坏后果 | 数据不准、请求变慢、偶发 500 | **身份伪造、密钥泄漏、内网探测** |
> | 是否可事后补救 | 可（改代码 + 重跑数据） | **往往不可（密钥一旦泄漏必须轮换；伪造的评论无法追溯）** |
>
> 因此 **§9 的 S-1 / S-2 / S-4 排在全部 B-* 之前**；S-3 / S-5 与 P1 同批但优先实施。

## 3. 线程池与并发

### B-01 [P0] `@Async` 方法在异步线程解引用 `HttpServletRequest`

**现状**（[StatsService.java:51-66](../backend/src/main/java/com/unicorn/studio/service/StatsService.java#L51-L66)）：

```java
@Async("asyncExecutor")
public void recordPv(String path, String referer, HttpServletRequest request) {   // ← 传的是 request 对象
    String ua = request.getHeader("User-Agent");              // ← 异步线程里解引用
    ... IpUtils.getClientIp(request) ...
}
```

调用点 [StatsController.java:33](../backend/src/main/java/com/unicorn/studio/controller/StatsController.java#L33) 把容器线程持有的 `HttpServletRequest` 直接交给了线程池。**Servlet 规范不允许在请求返回后访问 request**：Tomcat 会回收并复用该对象，此时 `getHeader` 可能读到**下一个请求的 User-Agent**（数据串号），或抛出 `IllegalStateException`。

**为什么这是 P0**：这不是理论风险——项目里 [AuditLogAspect.java:33-34](../backend/src/main/java/com/unicorn/studio/common/audit/AuditLogAspect.java#L33-L34) 的注释**已经明确警告过这个模式**并为此改成「在请求线程内构建实体」，`recordPv` 是唯一没遵循的地方。且 `recordPv` 的 `try/catch(Exception)` 会把异常吞成一行 WARN，**故障完全静默**，只会表现为「PV 数据对不上」，极难排查。

**修法**——把要用的字段在请求线程内提取完，只把值传进异步方法：

```java
// StatsController（请求线程内）
statsService.recordPv(path, referer,
        httpRequest.getHeader("User-Agent"),
        IpUtils.getClientIp(httpRequest));

// StatsService
@Async("asyncExecutor")
public void recordPv(String path, String referer, String userAgent, String clientIp) {
    try {
        VisitLog entry = VisitLog.builder()
                .pagePath(path == null || path.isBlank() ? "/" : path)
                .ipHash(IpUtils.sha256(clientIp))
                .ua(userAgent == null ? null : userAgent.substring(0, Math.min(userAgent.length(), 255)))
                .referer(referer)
                .visitedAt(LocalDateTime.now())
                .build();
        visitLogMapper.insert(entry);
    } catch (Exception e) {
        log.warn("PV 埋点写入失败: {}", e.getMessage());
    }
}
```

> 顺带：[VisitLog.referer](../backend/src/main/java/com/unicorn/studio/model/VisitLog.java) 对应列是 `VARCHAR(500)`，但 `referer` 未做截断，超长会被 MySQL 以严格模式拒绝（或静默截断），建议一并 `truncate 到 500`。

### B-02 [P0] `ChatClientFactory` 在 `computeIfAbsent` 内修改同一个 map

**现状**（[ChatClientFactory.java:53-59, 98-102](../backend/src/main/java/com/unicorn/studio/AIWorker/service/ChatClientFactory.java#L53-L59)）：

```java
return cache.computeIfAbsent(fingerprint, key -> {
    evictIfOversized();     // ← 内部在 cache.size() >= 16 时执行 cache.clear()
    return build(config);
});
```

`ConcurrentHashMap.computeIfAbsent` 的 Javadoc 明确规定：**mapping function 不得修改此 map**。在 mapping function 内 `clear()` 会导致：① 该 bin 的锁与其他线程的更新互相等待，**存在死锁风险**；② 其他线程并发写入的条目被无声丢弃；③ 某些 JDK 版本下抛 `IllegalStateException` / 表状态损坏。触发条件是「缓存达到 16 个指纹 + 又来一个新指纹」，即**管理员在后台改过几轮 AI 配置后必然踩到**。

**修法**——把淘汰挪到 `computeIfAbsent` 之外，并顺手把「整体清空」换成容量可控的写法：

```java
public ChatClient client(AiRuntimeConfig config, Object... tools) {
    String fingerprint = fingerprint(config);
    ChatClient cached = cache.get(fingerprint);
    if (cached != null) {
        return cached;
    }
    // 淘汰必须在 computeIfAbsent 之外完成
    evictIfOversized();
    return cache.computeIfAbsent(fingerprint, key -> build(config));
}
```

> 更稳妥的做法是用 `LinkedHashMap` + `removeEldestEntry`（配 `synchronized`）或引入 Caffeine 的 `maximumSize(16)`——**注意**：每个 value 是完整的 `OpenAiChatModel` + `OpenAiApi`（各自持有 HTTP 客户端资源），16 个实例的堆与 fd 开销不小，上限调低（如 4～8）比调高更合适。另外指纹含 `apiKey.hashCode()`（[:65](../backend/src/main/java/com/unicorn/studio/AIWorker/service/ChatClientFactory.java#L65)），**只换 Key 时旧实例不会被淘汰**，只能等 `clear()`。

### B-04 [P0] `@Async` 在 `finally` 中提交；队列满时异常覆盖业务返回值

**现状**（[AsyncConfig.java:22-31](../backend/src/main/java/com/unicorn/studio/config/AsyncConfig.java#L22-L31)）：

```java
pool.setCorePoolSize(2);
pool.setMaxPoolSize(8);
pool.setQueueCapacity(200);
pool.setThreadNamePrefix("async-");
pool.initialize();
```

**四个问题**，前两个已构成缺陷：

1. **异常从 `finally` 中抛出，覆盖业务结果**（[AuditLogAspect.java:86-91](../backend/src/main/java/com/unicorn/studio/common/audit/AuditLogAspect.java#L86-L91)）：

```java
} finally {
    entry.setDurationMs(...);
    writeAuditFile(entry);
    selfProvider.getObject().persist(entry);   // ← @Async 提交；队列满时在此抛 TaskRejectedException
}
```

   `@Async` 的**提交期**异常（`TaskRejectedException`）是**同步抛给调用方的**，而这里调用点在 `finally` 里——**从 `finally` 抛出的异常会取代 `try` 中的正常返回值或原始异常**。后果：**业务已成功落库，前端却收到 500**；若业务本身抛了异常，原始异常还会被这个提交异常**顶掉**，错误日志里看到的是 `TaskRejectedException` 而不是真正的故障原因。影响面是**所有 `@AuditLog` 标注的写接口**（作品/新闻/评论/账号/配置等）。

2. **备份会留下永久 `running` 僵尸记录**（[BackupService.java:78-87](../backend/src/main/java/com/unicorn/studio/admin/service/BackupService.java#L78-L87)）：`trigger()` 先 `insert` 一条 `status="running"` 的记录（自动提交），**之后**才提交异步任务。若提交被拒，[BackupController.java:42-45](../backend/src/main/java/com/unicorn/studio/admin/controller/BackupController.java#L42-L45) 返回 500，而那条记录**永远停在 `running`**——后台备份列表里出现一条永不结束的备份，且没有补偿逻辑。

3. **`maxPoolSize=8` 形同虚设**：`ThreadPoolTaskExecutor`（底层 `ThreadPoolExecutor`）的排队语义是「**核心线程满 → 全部进队列 → 队列满了才扩容到 max**」。队列容量 200，所以在积压 200 个任务之前，**实际并发度恒为 2**。
4. **两个消费者抢一个池**：`asyncExecutor` 同时服务 [StatsService.recordPv](../backend/src/main/java/com/unicorn/studio/service/StatsService.java#L51)（每次浏览一条 INSERT，高频）与 [AuditLogAspect.persist](../backend/src/main/java/com/unicorn/studio/common/audit/AuditLogAspect.java#L123)（后台操作，低频但重要）。高频的 PV 把队列灌满后，**审计日志会被一起拒绝**，而两者恰恰是「可以丢」与「绝不能丢」的两个极端。
5. **未设 `setWaitForTasksToCompleteOnShutdown` / `setAwaitTerminationSeconds`** → 关闭时在途任务直接丢弃（**含未落库的审计日志**）。

**修法**——按「业务重要性」拆池 + 显式拒绝策略：

```java
/** PV 埋点等可丢弃的弱一致任务：队列满时由调用线程兜底执行（CallerRuns），绝不抛异常 */
@Bean("statsExecutor")
public Executor statsExecutor() {
    ThreadPoolTaskExecutor pool = new ThreadPoolTaskExecutor();
    pool.setCorePoolSize(2);
    pool.setMaxPoolSize(2);
    pool.setQueueCapacity(500);
    pool.setThreadNamePrefix("stats-");
    pool.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
    pool.setWaitForTasksToCompleteOnShutdown(true);
    pool.setAwaitTerminationSeconds(10);
    pool.initialize();
    return pool;
}

/** 审计落库：不允许静默丢弃，队列满时同样 CallerRuns，让请求线程承担（可观测） */
@Bean("auditExecutor")
public Executor auditExecutor() { /* core=1, max=2, queue=500, CallerRunsPolicy */ }
```

> **`CallerRunsPolicy` 在这里是刻意的选择**：它把「系统过载」转化为「请求变慢」而不是「数据丢失 + 500」。若希望埋点在过载时直接丢弃，用 `DiscardPolicy` 也可以，但**必须显式选择**，不能靠默认的 `AbortPolicy` 抛异常。

### B-05 [P1] 5 个 `@Scheduled` 任务共用单线程调度器

**现状**：项目**没有定义 `TaskScheduler` bean**，`application.yml` 也没有 `spring.task.scheduling.pool.size`（已 grep 确认无配置）→ 全部 `@Scheduled` 落在 Spring Boot 自动配置的 `ThreadPoolTaskScheduler`，**池大小 = 1**。

当前 5 个任务：

| 任务 | 触发 | 耗时特征 |
|---|---|---|
| [StatsService.aggregateDaily](../backend/src/main/java/com/unicorn/studio/service/StatsService.java#L69) | `0 0 1 * * *` | 多表聚合，随 visit_log 增长变慢 |
| [BackupService.scheduledBackup](../backend/src/main/java/com/unicorn/studio/admin/service/BackupService.java#L187) | `0 0 2 * * *` | mysqldump 全库导出（**最慢**，触发后立即异步化，占用调度线程时间短） |
| [PublicUserAdminService.autoUnban](../backend/src/main/java/com/unicorn/studio/admin/service/PublicUserAdminService.java#L128) | `0 0 3 * * *` | 循环 `updateById`，N 次全列 UPDATE |
| [RetentionService.scheduledCleanup](../backend/src/main/java/com/unicorn/studio/admin/service/RetentionService.java#L283) | `0 30 3 * * *` | 单轮最多删 50000 行，**长事务** |
| [ViewCountService.flush](../backend/src/main/java/com/unicorn/studio/common/cache/ViewCountService.java#L57) | `fixedDelay 120s` | 每 2 分钟一轮，逐 key 2 次 Redis RTT + N 条 UPDATE |

**后果**：`flush` 每 2 分钟就要独占这唯一的线程；如果某轮脏 key 特别多（例如被爬虫刷了大量详情页），`flush` 耗时超过 2 分钟就会**持续挤占**调度线程，导致 01:00/03:30 的聚合与清理被推迟（`@Scheduled` 默认不并发，同一调度器上串行）。同时 `RetentionService` 的长事务跑在这个线程上，期间 Redis 回写全部停摆。

**修法**——显式定义带池的调度器（最小改动，一行配置也可）：

```yaml
spring:
  task:
    scheduling:
      pool:
        size: 4          # 5 个任务里同一时刻最多 2 个真正重叠，4 足够
      thread-name-prefix: sched-
```

或定义 bean 以支持 `@Scheduled` 的 `scheduler` 属性分流（长任务与心跳任务分开）：

```java
@Bean("schedulerPool")
public TaskScheduler schedulerPool() {
    ThreadPoolTaskScheduler s = new ThreadPoolTaskScheduler();
    s.setPoolSize(4);
    s.setThreadNamePrefix("sched-");
    s.setWaitForTasksToCompleteOnShutdown(true);
    s.setAwaitTerminationSeconds(60);
    s.initialize();
    return s;
}
```

> **同时建议**：`ViewCountService.flush` 的 `SMEMBERS` 无界（见 B-16），应先治根，否则开 4 个线程也只是把阻塞摊开。

### B-06 [P1] Tomcat 工作线程与 Druid 连接池严重失配；虚拟线程未启用

| Lettuce 连接池 | max-active 16 / max-idle 8 / min-idle 2 | [application.yml:79-83](../backend/src/main/resources/application.yml#L79-L83) |
| 虚拟线程 | **未启用**（Java 21 已具备） | 无 `spring.threads.virtual.enabled` |

**问题**：200 个 Tomcat 线程抢 10 个数据库连接，意味着**最多 190 个线程在 `max-wait: 10000`（10 秒）上排队**。一旦并发超过 10，请求延迟不再是「查询时间」而是「排队时间」，且 `max-wait` 超时后会抛 `GetConnectionTimeoutException` → 500。当前并发低所以没暴露，但这是**吞吐的硬上限**：整个应用的 QPS ≈ 10 / 平均查询耗时。

**还有一个容易忽略的连接占用**：`@Async` 线程也会消耗连接。一个带 `@AuditLog` 的写请求会**同时占用 2 条连接**——业务事务 1 条 + 异步审计落库 1 条（[AuditLogAspect.java:126](../backend/src/main/java/com/unicorn/studio/common/audit/AuditLogAspect.java#L126)）；备份任务（[BackupService.java:91,112](../backend/src/main/java/com/unicorn/studio/admin/service/BackupService.java#L91-L112)）在跑的时候也会额外占用。**实际有效并发要再打对折**，扩池时需把这一层算进去。

**修法**（分两步，不要一次全开）：

1. **先量化**：打开 actuator（B-19）观察 `druid` 与 Tomcat 的实际并发水位，再决定池大小。经验公式：`连接数 ≈ (核心数 × 2) + 有效磁盘数`，或直接 `连接数 = QPS × 平均查询耗时(s)`。本站规模建议 `max-active: 20`、`min-idle: 5`、`max-wait: 3000`（**缩短等待**，快速失败优于长时间挂起）。
2. **再考虑虚拟线程**：本项目绝大多数请求是「阻塞等 DB / 等 Redis」的 IO 密集型，正是虚拟线程的适用场景。但**开启前必须确认**：
   - 连接池仍是 10/20 个真实连接，虚拟线程再多也不能提高 DB 并发——所以**先扩池，再开虚拟线程**；
   - `synchronized` 块内的阻塞会 pin 住载体线程（Java 21 的 `synchronized` 仍是 pinning 点，JDK 24 才解决），需检查热点路径（Druid 内部有 `synchronized`）；
   - `-Djdk.virtualThreadScheduler.parallelism` 与限流策略需要重新评估（`RateLimitFilter` 走 Redis，无影响）。

```yaml
spring:
  threads:
    virtual:
      enabled: true      # 仅在完成第 1 步、且压测确认后开启
server:
  tomcat:
    threads:
      max: 200           # 虚拟线程下可保持默认；传统线程下建议 50
    accept-count: 200
    max-connections: 1000
```

### B-07 [P1] SMTP 发信在 `@Transactional` 内同步阻塞

**现状**（[MessageAdminService.java:53-67](../backend/src/main/java/com/unicorn/studio/admin/service/MessageAdminService.java#L53-L67)）：

```java
@Transactional
public void reply(Long id, String content, Long operatorId) {
    ...
    messageMapper.updateById(message);          // ← 事务已开启、连接已占用
    if (message.getContact() != null && message.getContact().contains("@")) {
        emailService.send(...);                 // ← 同步 SMTP，在同一事务内、同一请求线程上
    }
}
```

**问题**：SMTP 是**外部网络 IO**，配置为 465 端口 SSL（[application.yml:52-60](../backend/src/main/resources/application.yml#L52-L60)），建连 + 握手 + 投递通常是**数百毫秒到数秒**。这段时间里：

- **一个 Druid 连接被事务占住**（池只有 10 个）；
- **一个 Tomcat 线程被占住**；
- 若 SMTP 抛异常，会**连带回滚留言的 `replied` 状态**——管理员看到「回复失败」，但邮件可能已经发出去了，或者反之。

**更严重的是：邮件没有任何超时配置**。[application.yml:58-60](../backend/src/main/resources/application.yml#L58-L60) 只设了 `mail.smtp.auth` 与 `mail.smtp.ssl.enable`，**没有 `mail.smtp.connectiontimeout` / `timeout` / `writetimeout`**。JavaMail 的默认值是**无限等待**——SMTP 服务器接受 TCP 连接后不响应（网络黑洞、防火墙丢包、对端假死）时，这个请求会**永久挂起**，同时**永久占用一条数据库连接**。连接池只有 10 条，连续几次这样的挂起就能让**整个应用失去数据库连接**（`max-wait` 10 秒后所有请求 500）。这是「一个可选功能拖垮整个服务」的典型形态。

**修法**——把发信移出事务，并用独立线程池（复用 B-04 的 `auditExecutor` 或新建 `mailExecutor`）：

```java
@Transactional
public void reply(Long id, String content, Long operatorId) {
    Message message = getOrThrow(id);
    ... // 只做 DB 写
    messageMapper.updateById(message);
    // 事务提交后再发信；失败不影响业务，仅记日志
    String contact = message.getContact();
    if (contact != null && contact.contains("@")) {
        mailDispatcher.sendAfterCommit(contact, content, message.getContent());
    }
}
```

`sendAfterCommit` 内部用 `TransactionSynchronizationManager.registerSynchronization(...)` 的 `afterCommit` 回调投递到线程池；邮件失败**只记 WARN 不重抛**（与 `AuditLogAspect.persist` 的处理方式一致）。

**并且必须补上超时**（这是本节的关键，缺了它移出事务也只是把挂起从「占连接」变成「占线程」）：

```yaml
spring:
  mail:
    properties:
      mail.smtp.auth: true
      mail.smtp.ssl.enable: true
      mail.smtp.connectiontimeout: 5000    # 建连 5s
      mail.smtp.timeout: 10000             # 读 10s
      mail.smtp.writetimeout: 10000        # 写 10s
```

### B-30 [P2] 并发细节：冗余初始化、锁内查库、熔断覆盖面、事务内慢 IO

这一组是本次调查中**不足以单列 P1 但值得记录**的实现细节，建议在相邻改动中顺手处理：

**① `pool.initialize()` 是冗余调用**（[AsyncConfig.java:29,40](../backend/src/main/java/com/unicorn/studio/config/AsyncConfig.java#L29-L40)）：`ThreadPoolTaskExecutor` 的父类 `ExecutorConfigurationSupport` 实现了 `InitializingBean`，`afterPropertiesSet()` 就是调 `initialize()`；手工调用会**先建一个 ExecutorService 再被 `initialize()` 覆盖丢弃**。因为 `prestartAllCoreThreads` 默认 false（未启动线程），所以是**对象级浪费而非线程泄漏**，但属于该删的写法——直接删掉这两行即可。

**② 双检锁内做数据库查询**：[SensitiveWordService.java:55-72](../backend/src/main/java/com/unicorn/studio/service/SensitiveWordService.java#L55-L72)（DCL 写法本身正确，用了 `volatile`）与 [SiteSettingsService.java:137-149](../backend/src/main/java/com/unicorn/studio/admin/service/SiteSettingsService.java#L137-L149) 都在 `synchronized` 块内查库。首字穿透（缓存刚失效时）会把**热点评论/留言路径串行化**。建议改为「锁外查库 + 锁内只做赋值」，或让过期时不阻塞读（返回旧值 + 异步刷新）。

**③ 熔断器覆盖面不全**：[CacheCircuitBreaker](../backend/src/main/java/com/unicorn/studio/common/cache/CacheCircuitBreaker.java) **只被 `CacheHelper` 使用**。[RedisRateLimiter](../backend/src/main/java/com/unicorn/studio/common/cache/RedisRateLimiter.java)、[RefreshTokenStore](../backend/src/main/java/com/unicorn/studio/common/cache/RefreshTokenStore.java)、[ViewCountService](../backend/src/main/java/com/unicorn/studio/common/cache/ViewCountService.java) 各自 `catch` 降级，**不受熔断保护**——Redis 宕机时这些路径**每个请求都要白等一次超时**（`timeout: 300ms` / `max-wait: 200ms`，叠加起来可见）。建议把熔断器下沉为共用的降级开关。

**④ 事务内做慢 IO**（除 B-07 的 SMTP 外还有两处）：

| 位置 | 事务内的慢操作 |
|---|---|
| [FileService.java:63-129](../backend/src/main/java/com/unicorn/studio/admin/service/FileService.java#L63-L129) `@Transactional` | `ImageIO.read` 整图解码（[:87](../backend/src/main/java/com/unicorn/studio/admin/service/FileService.java#L87)）+ `Files.copy` 落盘（[:111-113](../backend/src/main/java/com/unicorn/studio/admin/service/FileService.java#L111-L113)）。上传 50MB 视频时**全程占用一条连接** |

| [AuthService.java:79-98](../backend/src/main/java/com/unicorn/studio/admin/service/AuthService.java#L79-L98)、[:116-128](../backend/src/main/java/com/unicorn/studio/admin/service/AuthService.java#L116-L128) `@Transactional` | 事务内做 Redis 读写（refresh 轮换 = GET + DB select + SET + DEL 全在同一事务里） |

  原则：**事务只包数据库操作**。文件写盘、图片解码、BCrypt、Redis、SMTP 都应移出事务边界。

### B-08 [P1] 评论列表假分页

**现状**（[CommentService.java:81-104](../backend/src/main/java/com/unicorn/studio/service/CommentService.java#L81-L104)）：

```java
List<Comment> approved = commentMapper
        .findByTargetTypeAndTargetIdAndStatusOrderByCreatedAtAsc(targetType, targetId, "approved");  // 无 LIMIT
List<Comment> roots = approved.stream().filter(c -> c.getParentId() == null).toList();   // 内存过滤
int from = Math.min(page * size, roots.size());
List<Comment> pageRoots = roots.subList(from, to);                                        // 内存分页
```

[CommentMapper](../backend/src/main/java/com/unicorn/studio/mapper/CommentMapper.java) 的该方法**没有 LIMIT**：一个 5000 条评论的热门作品，**每次翻任何一页都要把 5000 行（每行含最多 1000 字 content）全部拉回 JVM**，再过滤、再切页。`size` 参数完全不影响 DB 侧开销——这是教科书式的假分页。

**讽刺的是，同一个项目已经知道正确写法**：[CommentAdminService.java:51](../backend/src/main/java/com/unicorn/studio/admin/service/CommentAdminService.java#L51) 用了 `selectPage`，[CommentMapper.java:19-21](../backend/src/main/java/com/unicorn/studio/mapper/CommentMapper.java#L19-L21) 也有 `findByParentIdIn` 批量查询。

**修法**——一级评论走真分页，子评论按当页 rootIds 批量取（保持现有树深 2 的契约）：

```java
public Map<String, Object> listApproved(String targetType, Long targetId, int page, int size) {
    // ① 一级评论真分页（LIMIT），总数由 count 查询得出
    Page<Comment> rootPage = commentMapper.selectPage(
            new Page<>(page + 1, size),
            new LambdaQueryWrapper<Comment>()
                    .eq(Comment::getTargetType, targetType)
                    .eq(Comment::getTargetId, targetId)
                    .eq(Comment::getStatus, "approved")
                    .isNull(Comment::getParentId)
                    .orderByAsc(Comment::getCreatedAt));
    // ② 子评论按当页 rootIds 一次 IN 查询（复用既有 findByParentIdIn）
    Set<Long> rootIds = rootPage.getRecords().stream().map(Comment::getId).collect(Collectors.toSet());
    Map<Long, List<Comment>> childrenByParent = rootIds.isEmpty() ? Map.of()
            : commentMapper.findByParentIdIn(List.copyOf(rootIds)).stream()
                    .collect(Collectors.groupingBy(Comment::getParentId, LinkedHashMap::new, Collectors.toList()));
    List<Map<String, Object>> tree = rootPage.getRecords().stream()
            .map(root -> Map.<String, Object>of("comment", root,
                    "replies", childrenByParent.getOrDefault(root.getId(), List.of())))
            .toList();
    return Map.of("list", tree, "total", rootPage.getTotal());
}
```

> **注意**：`isNull(parentId)` 需要 `comment(parent_id, target_type, target_id, status, created_at)` 上的复合索引支撑，请对照 [mysql-migration-v15-index-tuning.sql](../backend/sql/mysql-migration-v15-index-tuning.sql) 确认；若缺失需补索引，否则真分页的 `COUNT` 仍会扫全表。

### B-10 [P1] 后台 13 个分页接口的 `size` 参数未钳制

```java
public static <T> Page<T> safePage(int page, int size) {
    return new Page<>(Math.max(1, page), Math.min(Math.max(1, size), 500));
}
```

   合计：**4 条 → 1 条，全站 14 条 → 11 条**（这是本节可达成的真实收益，不是 v1.0 写的「≤ 7」）。
3. 3 条裸 `COUNT(*)`（[:80/:83/:86](../backend/src/main/java/com/unicorn/studio/admin/service/DashboardService.java#L80-L86)，`work`/`news`/`public_user`）可合并为一次 `UNION ALL`，或接受（表小、有缓存）；

### B-15 [P2] UV 统计把全部去重 IP 拉进堆只为 `.size()`（**已实测降级**）

**现状**（[VisitLogMapper.java:17-26](../backend/src/main/java/com/unicorn/studio/mapper/VisitLogMapper.java#L17-L26)）：

```java

    QueryWrapper<VisitLog> qw = new QueryWrapper<VisitLog>()
            .select("distinct ip_hash")
            .ge("visited_at", from).lt("visited_at", to);
    ...
    return selectObjs(qw).stream().map(o -> String.valueOf(o)).toList();   // 全量物化
}
```

三个调用点**全都只取 `.size()`**：

| 调用点 | 区间 |
|---|---|
| [DashboardService.java:75](../backend/src/main/java/com/unicorn/studio/admin/service/DashboardService.java#L75) | 今日 |
| [DashboardService.java:77](../backend/src/main/java/com/unicorn/studio/admin/service/DashboardService.java#L77) | **30 天窗口** |
| [StatsService.java:83](../backend/src/main/java/com/unicorn/studio/service/StatsService.java#L83) | 昨日 |

**后果**：每次仪表盘缓存失效（TTL 仅 60s）都要把**整窗口内所有去重 IP 的 64 字符哈希串**从 MySQL 逐行搬到 JVM、转成 `String`、再数个数——纯粹为了得到一个整数。

> **勘误（v1.1）**：v1.0 此处写「以日均 5 万 UV 计算，一次就是 ~300 万个 String 对象、约 200MB+ 的瞬时分配」——**这个换算算错了**（把「日均去重数 × 窗口天数」当成了去重后的数量，而去重恰恰意味着不能相乘）。正确的量级关系是：
>
> ```
> 保留的 String 数 ≈ 该窗口内去重后的 IP 数 N        （不是 N_日 × 天数）
> 每个 64 字符 hex String ≈ 64B 字节数组 + ~32B 对象头/字段 ≈ 100B
> 保留堆 ≈ 100B × N；再加上 MyBatis 逐行物化的瞬时开销 ≈ 300B × N
> ```
>
> | 窗口内去重 IP 数 N | 保留堆（约） | 瞬时分配（约） |
> |---|---|---|
> | 5 万 | ~5 MB | ~15 MB |
> | 50 万 | ~50 MB | ~150 MB |
> | 200 万 | ~200 MB | ~600 MB |
>
> **结论要分情况**：N 小的时候（小站）这**不构成问题**，说「单点内存收益最大」是 v1.0 的**夸大**。但——**不论 N 大小，这份开销都是纯浪费**：`COUNT(DISTINCT)` 只回传一个整数，零行传输、零堆分配。真正要确认的是本站的 N 有多大。
>
> **✅ 已实测（2026-09-13，负责人于真实库执行）——本项据此从 P1 降为 P2**：
>
> ```
> visit_log 总行数          840
> 全表去重 ip_hash            1
> 近 30 天去重 ip_hash        1
> 今日去重 ip_hash            1
> 时间跨度           2026-09-03 ~ 2026-09-13
> ```
>
> **N = 1**。按上表换算，保留堆约 **100 字节**、瞬时分配约 **300 字节**——**不是百 MB 级**。v1.0/v1.1 的定级与「优先」标注均**高估**了本项。
>
> **结论**：
> 1. **B-15 降为 P2**，从阶段三的「优先」位置撤下；
> 2. 仍是**该做**的改动（「一条 SQL 换掉一段物化」成本极低、无风险，且能防止将来数据量上来后重新踩坑），只是**不必排在前面**；
> 3. **同样的实测也反证了 B-13 的收益被高估**——14 → 11 条查询在 840 行的表上毫无感知（见 B-13 的补充说明）；
> 4. **`distinct ip_hash = 1` 说明 UV 统计目前几乎没有真实数据**（埋点未被真实访问填充，或仅有本机访问）。因此 `DashboardService` 的 **UV 相关优化可整体后延**——在数据量上来之前，UV 路径的优化无法被验证，做了也不知道有没有用。
>
> **同时要澄清一点**：改成 `COUNT(DISTINCT)` **并不能减少 MySQL 侧的计算量**（它同样要算出 distinct 集合，同样可能走临时表/文件排序）。本项的收益**只在「行传输 + JVM 物化」这两段**——这也正是它值得做的地方：省下的是网络与堆，而 DB 侧的代价不变。

> **定级标注（v1.2 新增）**：本节保留 P2 定级，并**追加一句可复现的判据**——若将来 `SELECT COUNT(DISTINCT ip_hash) FROM visit_log WHERE visited_at >= NOW() - INTERVAL 30 DAY` 的结果 **≥ 50 万**，应**重新升回 P1**。请把该查询加入定期巡检，而非只在本次实施时看一次。

**修法**——加一个返回 `long` 的 SQL 聚合方法，替换三个调用点：

```java
/** 某段时间内的 UV（SQL 侧 COUNT(DISTINCT)，不物化明细） */
@Select("SELECT COUNT(DISTINCT ip_hash) FROM visit_log " +
        "WHERE visited_at >= #{from} AND visited_at < #{to}")

```

> 同类写法在 [VisitLogMapper.java:35-39](../backend/src/main/java/com/unicorn/studio/mapper/VisitLogMapper.java#L35-L39) 的 `findDailyPvUv` 里**已经有了**（`COUNT(DISTINCT ip_hash)`），本次只是补齐另一个方法。改造后 `findDistinctIpHashes` 若再无调用者可删除。
>
> **索引**：`idx_visit_log_ip (ip_hash, visited_at)` 与 `idx_visit_log_time (visited_at)` 已存在（[mysql-init.sql:306-307](../backend/sql/mysql-init.sql#L306-L307)），`COUNT(DISTINCT)` 可走索引，无需新增。

### B-16 [P1] `ViewCountService.flush` 无界 `SMEMBERS` + 逐 key 2 次 Redis 往返

**现状**（[ViewCountService.java:57-100](../backend/src/main/java/com/unicorn/studio/common/cache/ViewCountService.java#L57-L100)）：

```java
keys = redis.opsForSet().members(CacheKeys.VIEW_DIRTY);   // :61 把整个脏索引 Set 读进内存
for (String key : keys) {
    raw = redis.opsForValue().getAndDelete(key);          // :75  第 1 次 RTT
    redis.opsForSet().remove(CacheKeys.VIEW_DIRTY, key);  // :76  第 2 次 RTT
    ...
    apply(key, delta);                                    // :94  单条 DB UPDATE
}
```

**三个问题**：

1. **`SMEMBERS` 无界**：脏索引的成员数 = 本轮被浏览过的不同作品/新闻数。**每个被浏览过的 id 会常驻**（TTL 7 天，且每次 `increment` 都续期，见 [:45](../backend/src/main/java/com/unicorn/studio/common/cache/ViewCountService.java#L45)）。被爬虫批量扫详情页时，这个 Set 可以涨到数万条。
2. **每 key 2 次 Redis 往返**：`GETDEL` + `SREM` 可以合并为**一次 `Lua` 脚本**或 pipeline，N 个 key 就是 2N 次 RTT → 可降到 N 次（Lua）甚至 1 次（pipeline 批量）。
3. **`SREM` 在 DB 写成功之前执行**（[:76](../backend/src/main/java/com/unicorn/studio/common/cache/ViewCountService.java#L76) 早于 [:94](../backend/src/main/java/com/unicorn/studio/common/cache/ViewCountService.java#L94) `apply`）：写库失败后靠 `reMarkDirty` 补回（[:122-128](../backend/src/main/java/com/unicorn/studio/common/cache/ViewCountService.java#L122-L128)）——逻辑是自洽的，但**若进程在 SREM 之后、apply 之前崩溃，这批增量会永久丢失**（计数偏低且无人知晓）。

**修法**（按性价比排序）：

1. **`SMEMBERS` 换 `SSCAN`**（游标分批，每批 500），把无界读变成有界流式处理；
2. **`GETDEL` + `SREM` 合并为 Lua**（与项目已有的 [RedisRateLimiter](../backend/src/main/java/com/unicorn/studio/common/cache/RedisRateLimiter.java) Lua 风格一致）：

```lua
-- KEYS[1]=dirty set, KEYS[2]=view key  → 返回增量并同时移出脏索引
local v = redis.call('GETDEL', KEYS[2])
redis.call('SREM', KEYS[1], KEYS[2])
return v
```

3. **批量 UPDATE**：同一张表的多个 id 增量可合并为一条 `UPDATE ... SET view_count = view_count + CASE id WHEN ... END WHERE id IN (...)`，或直接累计到内存后按表分组执行。

## 5. 内存占用优化

### B-17 [P1] 图片上传 `ImageIO.read` 无像素上限

**现状**（[FileService.java:85-93](../backend/src/main/java/com/unicorn/studio/admin/service/FileService.java#L85-L93)）：

```java
if (isImage) {
    try (InputStream in = file.getInputStream()) {
        BufferedImage image = ImageIO.read(in);      // 整体解码成光栅
        if (image == null) { throw ...; }
    }
}
```

体积校验只看**压缩后**的字节数（图片 10MB / 视频 50MB，[:77-83](../backend/src/main/java/com/unicorn/studio/admin/service/FileService.java#L77-L83)），**没有像素/尺寸上限**。

**风险**：一个 10MB 的 PNG 可以声明 10000×10000 像素——`ImageIO.read` 会把它解成 `int[]` 光栅，即 **10000 × 10000 × 4B ≈ 400MB 堆**（解压比可达 40000:1，经典「解压炸弹」）。**单个上传请求即可 OOM**，且因为 `application.yml` 里没有任何 `-Xmx`（B-18），JVM 默认堆是物理内存的 1/4，8GB 机器上 2GB 堆，一次这样的上传就能打挂服务。另外 `ImageIO` 默认 `useCache=true` 会**往临时目录写缓存文件**，与流式落盘的初衷相悖。

**修法**——两处都要做：

```java
// ① 先读头部拿尺寸，超限直接拒（不解码像素）
try (ImageInputStream iis = ImageIO.createImageInputStream(file.getInputStream())) {
    Iterator<ImageReader> readers = ImageIO.getImageReaders(iis);
    if (!readers.hasNext()) { throw BusinessException.badRequest("文件内容不是合法图片"); }
    ImageReader reader = readers.next();
    try {
        reader.setInput(iis, true, true);           // ① seekForwardOnly=true ② ignoreMetadata=true
        int w = reader.getWidth(0), h = reader.getHeight(0);
        if ((long) w * h > MAX_PIXELS) {            // 例如 40_000_000（约 4000×10000）
            throw BusinessException.badRequest("图片尺寸过大（最大 " + MAX_PIXELS / 1_000_000 + " 百万像素）");
        }
    } finally {
        reader.dispose();
    }
}

// ② 关闭 ImageIO 磁盘缓存（全局，启动时设一次）
ImageIO.setUseCache(false);
```

> 若保留「重解码验证」这一步（防二次渲染/伪装文件），也应改为 `reader.read(0, param)` 并配 `ImageReadParam` 做**降采样读取**，而不是全尺寸解码。

### B-18 [P1] 无任何 JVM 堆/GC 参数

**现状**（已穷尽搜索确认）：全项目**没有** `-Xmx` / `-Xms` / GC 选择 / `-XX:+HeapDumpOnOutOfMemoryError`，也没有 Dockerfile、docker-compose、`.sh`/`.bat` 启动脚本、`.mvn/jvm.config`、README 部署说明；`.vscode/launch.json` 无 `vmArgs`，`.idea/` 无 `VM_PARAMETERS`。

**后果**：以 **JVM 默认 `MaxHeapSize = 物理内存 / 4`** 运行——无堆上限意识、无 GC 选择（Java 21 默认 G1，尚可）、**OOM 时无堆转储**（排查等于盲猜）、无 `-XX:+ExitOnOutOfMemoryError`（OOM 后进程可能带病存活）。

**修法**——给出明确的启动参数，并落到文档（本项目无启动脚本，建议在 `docs/` 或 README 中固化）：

```
-Xms512m -Xmx1g
-XX:+UseG1GC
-XX:MaxGCPauseMillis=200
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=./logs/heapdump.hprof
-XX:+ExitOnOutOfMemoryError
-Dfile.encoding=UTF-8
-Duser.timezone=Asia/Shanghai
```

> **堆大小怎么定**：本站规模（单体 + 连接池 10）建议 `-Xmx1g` 起步；**当前的堆风险点是 B-17 的图片解压炸弹**（实测 `visit_log` 仅 840 行、UV 物化不存在风险，见 B-15），先修它，`1g` 足够宽裕。**不建议设得过大**——堆越大，G1 的单次 Full GC 停顿越久，而本站对象生命周期普遍很短。
>
> `-Dfile.encoding=UTF-8` 是必须的：项目为修复 Windows 控制台中文乱码把**控制台**编码设成了 GBK（[application.yml:192-194](../backend/src/main/resources/application.yml#L192-L194)），若 `file.encoding` 跟随系统代码页，文件与网络编码会受影响。

> ### ⚠️ S-6：actuator 的暴露面必须落到**代码级要求**，不是一句「注意」
>
> v1.0 只在文末提了一句「仅本机监听（现状）」。这**不够**——因为 `server.address: 127.0.0.1` 是**部署级**的，改一行配置就能失效，而 actuator 的暴露面是**代码级**的安全边界。实施 B-19 时必须同时满足：

>    management:
>      server:
>        port: 8081          # 独立端口，防火墙只放行内网
>        address: 127.0.0.1
>    ```
> 2. **业务链路上的拦截**：给 actuator 路径加一条**独立的、默认拒绝**的 `SecurityFilterChain`（`@Order(0)`，早于现有 `/api/admin/**` 与 `/api/**` 两条链），仅放行内网来源或携带管理凭证；**绝不能落在 `/api/**` 的 `permitAll` 链里**。
> 3. **生产默认不暴露 `heapdump`**：`heapdump` 只在需要排查时**临时**打开。`/actuator/heapdump` 会导出**整个堆**——其中驻留着 **`AiRuntimeConfig` 里已解密的明文 API Key**（该类注释自述「持有的是已解密的明文 apiKey，仅存在于服务端内存」），以及 Redis 口令、数据库口令等一切运行时明文。**一次未授权下载 = 全部密钥泄漏**。
> 4. **`env` / `configprops` / `beans` 一律不暴露**：它们会回显 `application.yml` 解析后的属性值（含 `${DB_PASSWORD:...}` 的实际取值）。
> 5. 若确实需要长期可用的 `heapdump`，改为**离线获取**（`jcmd <pid> GC.heap_dump /path`，走运维通道），不通过网络端点。

**同时把 `/api/health` 改成真探依赖**（这本就是《升级方案.md》的待办，且负载均衡/监控依赖它）：

```java
@GetMapping("/health")
public ApiResponse<Map<String, Object>> health() {
    boolean db = isDbUp();       // SELECT 1，带 200ms 超时
    boolean redis = isRedisUp(); // PING，带 200ms 超时
    return ApiResponse.ok(Map.of("ok", db && redis, "db", db, "redis", redis));
}
```

> **注（v1.2）**：v1.0 此处另有一段「actuator 端点必须只在内网/本机暴露……否则 `heapdump` 等于任意人可下载整个堆」的提醒——其要点**已被上方 S-6 提示框完全覆盖**（且后者更完整：补了独立端口、独立过滤器链、`env`/`configprops` 与 `jcmd` 离线获取）。为免读者认为两处要求不同，**该重复段落已删除**，以 S-6 提示框为准。

### B-20 [P2] `JwtAuthFilter` 每个后台请求都查库

**现状**（[JwtAuthFilter.java:50-53](../backend/src/main/java/com/unicorn/studio/admin/security/JwtAuthFilter.java#L50-L53)）：每个带 Bearer 的 `/api/admin/**` 请求都执行 `sysUserMapper.selectById(userId)`。这是**有意的安全取舍**（[AdminPermissionService.java:33-34](../backend/src/main/java/com/unicorn/studio/admin/service/AdminPermissionService.java#L33-L34) 明确写了「账号状态不缓存，禁用/删除即时生效，不引入越权窗口」）——权限码走 Redis 10 分钟缓存，账号状态刻意实时。

**代价**：它是**所有后台接口的固定 1 次 DB 往返**，配合 `max-active: 10` 直接参与吞吐上限。

**修法：不要自行设计，直接对齐 V15 §6.3 的既定方案**（v1.1 勘误 4）

> **勘误（v1.1）**：v1.0 此处自拟了一个「TTL 60s + 短 TTL 兜底」的方案——**这与 V15 §6.3 已经评审定稿的设计不一致**，属重复设计且参数相悖。V15 §6.3 早已把 `cache:auth:user:{userId}` 定义为 **TTL 5 min**、并给出**完整的失效点表**；v1.1 更把它**升格为「安全边界」而非性能问题**，落进**附录 C.1 安全验收（不通过则不得上线）**。本节一律以 V15 为准。

**关键事实（实施前必须知道）**：

1. **V15 §6.3 设计的 `cache:auth:user` 至今没有实现**——代码里 grep `cache:auth:user` **零命中**；[AdminPermissionService](../backend/src/main/java/com/unicorn/studio/admin/service/AdminPermissionService.java) 只实现了 `cache:auth:perm:`（10 min）。当前 [JwtAuthFilter.java:53](../backend/src/main/java/com/unicorn/studio/admin/security/JwtAuthFilter.java#L53) 走的是**实时 `selectById`**。
2. **这是一个刻意的、更严格的选择**：实时查库让 V15 附录 C.1 的第一条验收（「禁用管理员**下一次请求即 401**，不必等 5 min TTL」）**天然成立**。换成缓存后，这条验收就从「白送」变成「**必须靠失效链路保证**」。
3. 因此 B-20 的定位**不是「补一个漏掉的优化」，而是「用安全边界的松动换取每请求 1 次 DB 往返」**——收益是明确的（后台每个接口省 1 次查库），代价是**必须把 §6.3 失效表的每一行都实现并配集成测试**。

**若决定实施，验收标准直接引用 V15 附录 C.1**（`docs/Redis缓存设计设计方案.md`，逐条打勾）：

- [ ] 禁用管理员即时生效（`update(id, status=0)` 后下一次请求即 401/403）
- [ ] 降权即时生效（角色移除 `system:sql` 后下一次请求即 403）
- [ ] 改角色权限即时生效（`RoleService.update` 后该角色下**每个** `cache:auth:perm:{userId}` 均已清除）
- [ ] 删除管理员即时生效（`cache:auth:user:{id}` 与 `cache:auth:perm:{id}` 均不存在，且旧 refreshToken 不可用）
- [ ] 改密即时生效（清 `cache:auth:user:{id}`）
- [ ] 失效覆盖面穷举：§6.3 失效表**每一行**都有对应断言
- [ ] 兜底入口可用（命名空间级清空）
- [ ] **缓存中无敏感字段**：遍历 `cache:auth:user:*` 断言**不含 `password` / `refreshToken`**

> ⚠️ **最后一条尤其重要**：`SysUser` 实体带有 `password`（BCrypt 哈希）与 `refreshToken` 两个字段。**绝不能把 `SysUser` 实体直接塞进 Redis**。V15 §6.3 已规定缓存里**只放这 6 个字段**：
>
> ```
> id / username / nickname / avatar / status / mustChangePassword
> ```
>
> 把 `refreshToken` 写进 Redis 等于**新增一份可窃取的会话凭据**；把 `password` 哈希写进去则在 Redis 被攻破时把离线爆破的难度从「bcrypt 成本」降为「拿到哈希」（可无损用于撞库）。
>
> **注**：V15 §6.3 代码骨架里的 `AdminUserVO` 是**示意变量名，不是文档定义过的类契约**——实施时按上述 6 字段新建一个脱敏 VO 即可（项目里已有手写静态工厂的风格可循，见 `vo/` 目录），**不要去找一个不存在的 `AdminUserVO` 类**。

> **决策归属**：这**必须由负责人拍板**，不能由实施者自行决定。**保持现状也是完全可接受的选项**——它对安全更有利，代价仅是每请求一次主键查询（在有缓存兜底的今天，这是可接受的成本）。

### B-21 [P2] 审计切面在请求线程做两遍序列化

**现状**（[AuditLogAspect.java:158-177](../backend/src/main/java/com/unicorn/studio/common/audit/AuditLogAspect.java#L158-L177)）：

```java
return objectMapper.writeValueAsString(nodes);   // ③ 树再序列化成字符串
```

每个 `@AuditLog` 写接口都付「**两遍序列化 + 一棵完整 JsonNode 树 + 一次递归遍历**」的成本，且发生在 [:76](../backend/src/main/java/com/unicorn/studio/common/audit/AuditLogAspect.java#L76) `pjp.proceed()` **之前**、**请求线程内**（因为要拿 ThreadLocal 里的用户与请求信息）。另外 [:100-111](../backend/src/main/java/com/unicorn/studio/common/audit/AuditLogAspect.java#L100-L111) 的 `String.format`（10 个参数）+ 同步写文件也在这个线程上。

### B-23 [P2] 富文本消毒无输入长度上限；读路径消毒未实现

**现状**（[HtmlSanitizer.java:73-79](../backend/src/main/java/com/unicorn/studio/common/HtmlSanitizer.java#L73-L79)）：`Jsoup.clean(html, "", SAFELIST)` **没有输入长度上限**。jsoup 会先把整段 HTML 解析成**完整 DOM**（每个标签/属性/文本节点各一个对象），峰值堆可达原串的数倍。而 `content` 列是 MEDIUMTEXT（16MB），`WorkAdminService.WorkForm` 等表单 record **没有任何 `@Size` 约束**——一次 16MB 的提交即可让 DOM 化吃掉数百 MB 堆。

**同时存在注释与实现不符**：[HtmlSanitizer.java:17](../backend/src/main/java/com/unicorn/studio/common/HtmlSanitizer.java#L17) 声称「保存与前台输出前各跑一次 `clean()`（双保险）」，但实际**只在写入路径消毒**（`WorkAdminService:90,132`、`NewsAdminService:87,127`、`LearningAdminService:57,82`），读路径（[WorkService.java:50-63](../backend/src/main/java/com/unicorn/studio/service/WorkService.java#L50-L63)、[NewsService.java:44-55](../backend/src/main/java/com/unicorn/studio/service/NewsService.java#L44-L55)）**并未消毒**。

**顺带一个功能缺陷**：[HtmlSanitizer.java:21,24-34](../backend/src/main/java/com/unicorn/studio/common/HtmlSanitizer.java#L21-L34) 的 `configureAllowedOrigins` **全仓无调用者** → `app.upload.image-allow-origins`（[application.yml:132](../backend/src/main/resources/application.yml#L132)）配置完全失效，富文本外链图恒被拒。

**修法**：

1. 表单 DTO 加 `@Size(max = 200_000)` 之类的正文上限（**明确取值并写进注释**），消毒前先判长度；
2. 把 [:17](../backend/src/main/java/com/unicorn/studio/common/HtmlSanitizer.java#L17) 的注释改成与实现一致（**只写「保存前消毒」**），或补上读路径消毒——**二选一，不要留着误导后人**；
3. 补 `configureAllowedOrigins` 的调用（启动时从 `app.upload.image-allow-origins` 注入），并加同步保护（当前 `ALLOWED_DOMAINS` 是可变 `static HashSet`，配置写入与请求读取之间无 happens-before 保证）。

### B-25 [P2] 日志：4 个同步 appender、单文件无上限、控制台常开

**现状**（[logback-spring.xml:22-93](../backend/src/main/resources/logback-spring.xml#L22-L93)）：`root` 挂了 **CONSOLE + INFO_FILE + WARN_FILE + ERROR_FILE 四个 appender**，且**全部是同步 appender**——每条日志事件都要在**业务线程**上完成「格式化 + 4 次 appender 判定 + 1 次磁盘写入」。

**三个问题**：

1. **同步落盘拖慢请求线程**：`AccessLogFilter` 对每个 `/api/**` 请求打一条 INFO（[:76](../backend/src/main/java/com/unicorn/studio/common/log/AccessLogFilter.java#L76)），这条日志的磁盘写入**直接加在请求延迟上**。
2. **单文件无大小上限**：所有 `RollingFileAppender` 只用 `TimeBasedRollingPolicy` + `maxHistory=30`，**没有 `maxFileSize`**（[:12-13](../backend/src/main/resources/logback-spring.xml#L12-L13) 的注释自认这一点）。按天分目录能限制「一天一个文件」，但**单日写入量无上限**——一旦出现日志风暴（异常循环打日志），单个文件可以涨到 GB 级。
3. **控制台 appender 在生产常开**：`console-appender.xml` 走 GBK 编码（[application.yml:192-194](../backend/src/main/resources/application.yml#L192-L194) 为修 Windows 乱码而设），每次写入都要做**字符集转换**，而生产环境（systemd/重定向到文件）往往并不需要控制台输出。

**修法**：

```xml
<!-- ① 包一层 AsyncAppender，把磁盘 IO 移出业务线程 -->
<appender name="ASYNC_INFO" class="ch.qos.logback.classic.AsyncAppender">
    <queueSize>1024</queueSize>
    <discardingThreshold>0</discardingThreshold>   <!-- 0 = 队列满时也不丢，宁可阻塞 -->
    <neverBlock>false</neverBlock>
    <appender-ref ref="INFO_FILE"/>
</appender>

<!-- ② 用 SizeAndTimeBasedRollingPolicy 补上单文件上限 -->
<rollingPolicy class="ch.qos.logback.core.rolling.SizeAndTimeBasedRollingPolicy">
    <fileNamePattern>${LOG_PATH}/info/%d{yyyy-MM-dd}/app-info.log.%i</fileNamePattern>
    <maxFileSize>50MB</maxFileSize>
    <maxHistory>30</maxHistory>
    <totalSizeCap>2GB</totalSizeCap>
</rollingPolicy>
```

③ 生产 profile 下摘掉 CONSOLE appender（`<springProfile name="!dev">` 包裹 root 的 appender 列表）。

> **`discardingThreshold` 的取舍**：设为 0 表示队列满时**不丢弃**日志（阻塞业务线程），这保住了「审计日志不丢」但牺牲了「日志不拖慢请求」。对**审计 appender** 建议如此；对 **ACCESS 日志**可以放宽（丢弃比阻塞好）。这正是需要区分两个 appender 的原因。

### B-26 [P2] 备份子进程从不 `destroy()`；`deleteByPattern` 无界累积

**① mysqldump 子进程无回收**（[BackupService.java:130-150](../backend/src/main/java/com/unicorn/studio/admin/service/BackupService.java#L130-L150)）：`Process` 从未调用 `destroy()` / `destroyForcibly()`。`finally`（[:147-150](../backend/src/main/java/com/unicorn/studio/admin/service/BackupService.java#L147-L150)）只删临时凭据/错误文件。若 `in.transferTo(out)`（[:139](../backend/src/main/java/com/unicorn/studio/admin/service/BackupService.java#L139)）因磁盘满或 gzip 异常抛错，**mysqldump 子进程可能继续存活**，占住数据库连接与文件句柄（备份线程池只有 1 个线程，泄漏会累积）。

```java
Process process = null;
try {
    process = builder.start();
    ...
} finally {
    if (process != null && process.isAlive()) {
        process.destroyForcibly();          // 补上
    }
    // 既有的临时文件清理
}
```

**② `deleteByPattern` 无界累积**（[CacheHelper.java:147-164](../backend/src/main/java/com/unicorn/studio/common/cache/CacheHelper.java#L147-L164)）：用 `SCAN`（count 100）遍历，但把**所有命中 key 累积进 `ArrayList`**（[:152-156](../backend/src/main/java/com/unicorn/studio/common/cache/CacheHelper.java#L152-L156)）后才一次 `DEL`。当前调用方只有 `cache:auth:perm:*` 与 `cache:site:group:*`（量小，安全），但**pattern 一旦扩散**（例如误用 `cache:*`）就会变成无界内存操作。建议边 scan 边分批 DEL（每 500 个一批）。

**③ 另一处同类问题**：[BackupService.java:171](../backend/src/main/java/com/unicorn/studio/admin/service/BackupService.java#L171) 的 `findAllByOrderByCreatedAtDesc()` **全表载入内存**只为保留最近 N 条，应改为 `LIMIT`/`OFFSET` 或按 `created_at` 条件删除。

### B-27 [P2] `IpUtils.sha256` 重建 `MessageDigest`；敏感词 O(n) 扫描

**① `MessageDigest` 每次新建**（[IpUtils.java:20-32](../backend/src/main/java/com/unicorn/studio/common/IpUtils.java#L20-L32)）：每次调用都做 provider 查找 + `MessageDigest.getInstance("SHA-256")`。调用点在**热点路径**上：[StatsService.java:57](../backend/src/main/java/com/unicorn/studio/service/StatsService.java#L57)（每个 PV）、[CommentService.java:74](../backend/src/main/java/com/unicorn/studio/service/CommentService.java#L74)（每条评论）。`MessageDigest` **非线程安全**，正解是 `ThreadLocal<MessageDigest>`：

```java
private static final ThreadLocal<MessageDigest> SHA256 =
        ThreadLocal.withInitial(() -> {
            try { return MessageDigest.getInstance("SHA-256"); }
            catch (NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
        });
```

> 注意：`ThreadLocal` + 线程池要配 `remove()`；但这里是**固定复用同一 digest 实例**（`reset()` 而非持有业务数据），不构成泄漏。也可直接换 `org.apache.commons.codec.digest.DigestUtils`（已是传递依赖）或 Guava 的 `Hashing.sha256()`（内部已是 ThreadLocal）。

**② 敏感词 O(n) 全表扫描**（[SensitiveWordService.java:33-44](../backend/src/main/java/com/unicorn/studio/service/SensitiveWordService.java#L33-L44)）：`findSensitive` 对**每条评论内容逐词** `text.contains(word)`。词表规模由 `site_settings['notify.sensitive_words']` 决定，中等词表（数千词）× 每条评论 1000 字 = 可观的 CPU。正解是 **AC 自动机（Aho–Corasick）**——但实现成本不低，**建议列入 P2 待词表规模真的上来再做**，当前先记录。

**③ 同类**：[SensitiveWordService.java:26](../backend/src/main/java/com/unicorn/studio/service/SensitiveWordService.java#L26) 的 `cachedWords` 是**进程内常驻、无 TTL 无上限**，且 `invalidate()` 只清当前实例——**多实例部署时**，另一个实例改了词库，本实例的旧词库会永久生效（`SiteSettingsService:118-120` 只在本实例写入且 key 命中时调用 invalidate）。多实例部署前必须改为 Redis 失效广播或短 TTL。

### B-28 [P2] `SiteSettingsService` 双份缓存

**现状**（[SiteSettingsService.java:52-53](../backend/src/main/java/com/unicorn/studio/admin/service/SiteSettingsService.java#L52-L53)）：`volatile Map<String,Object> publicCache` + `volatile long publicCacheAt`（JVM 内，TTL 10 分钟），**同时**又通过 Redis 缓存 `cache:site:group:*`（[:74-84](../backend/src/main/java/com/unicorn/studio/admin/service/SiteSettingsService.java#L74-L84)）——**同一份数据在两个地方各存一份**。

**问题**：① 内存双份持有；② `invalidatePublicCache()` 只清本实例，**多实例下读旧值**；③ 类注释说「前台未接入」已过时——[SiteSettingsController.java:23](../backend/src/main/java/com/unicorn/studio/controller/SiteSettingsController.java#L23) 确实在对外暴露它。

**修法**：**保留 Redis 一份即可**（Redis 层已经有完整的失效链路 `evictAfterCommit`）。删掉 JVM 缓存能同时消除「双份内存」与「多实例不一致」两个问题，代价是每次读多一次 Redis RTT（<0.5ms，且 Redis 不可用时自动回源 MySQL，行为不变）。

> `getValue`（[:124-128](../backend/src/main/java/com/unicorn/studio/admin/service/SiteSettingsService.java#L124-L128)）**显式不走缓存**，被 `RetentionService` 每次执行调用——这是 N+1（B-11）之外的又一条冗余查询，建议一并纳入。

## 6. 分阶段实施计划

**阶段划分原则**：先修**正确性**（P0，改动小、风险低、收益明确），再修**吞吐与响应**，然后**内存与查询**，最后**基线与参数**。每阶段结束都应可独立上线、可独立回滚。

### 阶段零：安全修复（**先于全部性能项**，P0）

> **为什么是「阶段零」而不是「阶段一」**：本节三项 P0 的**利用门槛是「读过本仓库」**，且后果**不可事后补救**（密钥/口令一旦泄漏必须轮换，伪造的评论无法追溯）。而阶段一的 B-01 需要在**高并发下**才会暴露。**先修安全，再修性能**——详见 §1 的排序规则框与 §9。

| 项 | 改动 | 备注 |
|---|---|---|
| S-1 | yml 补 `app.public.jwt-secret: ${PUBLIC_JWT_SECRET:}`；构造函数照抄 `JwtService` 的 ≥32 字符启动守卫；`resolveFromHeader` 补 `status` 校验 | **必须同时轮换密钥**（旧字面量已进 git 历史） |
| S-4 | yml 口令默认值清空（`REDIS_PASSWORD` / `DB_PASSWORD` / `REDIS_HOST`），启动校验非空 | **必须轮换 Redis 凭据**；并核实**四项暴露面**：主机是否公网、**安全组是否放行 6379**、`bind` 配置、`protected-mode` |
| S-2 | `CryptoService` 改 fail-closed（显式开关才允许明文降级）；不再回退 `jwt-secret`；修 `deriveKey` 注释；长度阈值统一为 32 | 换密钥前**先在后台重填 API Key** |
| S-7 | 引入 `trustedProxyCount`（默认 **0** = 不信任 XFF），`IpUtils` 与 `AccessLogFilter` 共用；先确认生产拓扑 | 默认值必须安全；代理侧配合改 `proxy_set_header` |
| S-3 | `apiUrl` 校验（仅 https + 拒私网/环回/链路本地 + 建议厂商域名白名单），**探测与保存两条路径都要** | 注意 DNS rebinding |

> **验收**：§9.9 末尾的自查脚本全绿；**S-1/S-4 的凭据轮换完成后，旧 token 与旧口令全部失效**。
>
> **⚠️ S-1 的可执行验收（v1.2 修订，替换 v1.1 的错误写法）**：
>
> v1.1 写的是「用手工签发的伪造 token 访问 `/api/auth/me` 返回 401」——**这句话有两处错误，照做会误判为「没修好」**：
>
> 1. **`/api/auth/me` 不存在**。[PublicAuthController](../backend/src/main/java/com/unicorn/studio/controller/PublicAuthController.java#L12-L44) 只有 `POST /api/auth/register` 与 `POST /api/auth/login` 两个端点，**没有 `me`**。
> 2. **断言方向错了**。S-1 的修法是让 [`resolveFromHeader`](../backend/src/main/java/com/unicorn/studio/service/PublicAuthService.java#L80-L91) **`return null`（降级为游客）**——与 `JwtAuthFilter` 同口径，**不是抛 401**。所以伪造/失效的 token 会让请求**正常返回 200**，只是身份变成游客。**若按 401 断言，实施者会以为没生效。**
>
> **正确的验收步骤**（用伪造 token 发一条评论，然后查库看归属）：
>
> ```bash
> # 1) 用「旧字面量」密钥手工签一个 sub=1 的 token（替换 <FORGED>）
> #    header: {"alg":"HS256","typ":"JWT"}  payload: {"sub":"1","iat":...,"exp":...}
> #    HMAC-SHA256 密钥 = public-dev-secret-please-override-0123456789
>
> # 2) 用它发一条评论
> curl -s -X POST http://127.0.0.1:8080/api/comments \
>      -H "Content-Type: application/json" \
>      -H "Authorization: Bearer <FORGED>" \
>      -d '{"targetType":"work","targetId":1,"content":"验收用评论"}'
> ```
>
> ```sql
> SELECT user_id, guest_nickname FROM comment ORDER BY id DESC LIMIT 1;
> -- 修好前：user_id = 1        （token 被采信 → 身份被伪造成功）
> -- 修好后：user_id IS NULL    （token 被拒 → 降级为游客）
> ```
>
> **`user_id IS NULL` 就是 S-1 的通过标准**（前提是评论接口对游客开放，当前是——仅要求游客填 `guestNickname`）。若想额外验证「被禁言用户无法评论」，需把该用户 `status` 置 0 后重跑，期望返回 **403**（`CommentService` 的禁言校验）。

### 不建议做的事（明确排除）

- **不要引入 `@EnableCaching` / Spring Cache 抽象**：现有 `CacheHelper` 已实现穿透哨兵、TTL 抖动、熔断、`evictAfterCommit` 等 Spring Cache 不直接提供的能力，替换是净负收益。
- **不要给 `content` 加 `@TableField(select = false)`**：那会让**详情页**也查不到正文，属于破坏功能。必须在**具体查询**上做投影。
- **不要用 `updateById` 去改浏览量**（`WorkMapper` 的注释已说明）；也不要为了省一次查询给账号状态加长 TTL。
- **不要在未补索引的情况下把假分页改真分页**——可能比现在更慢。

## 9. 安全审查

> **为什么单列一章**：本文档 v1.0 **完全没有安全章节**，这是它的最大缺陷——一份只谈吞吐/内存的优化方案，会让人误以为「性能问题就是最该先修的」。而事实上本文档列出的安全项中，有三项的**利用门槛低到「读过本仓库即可」**，后果（身份伪造、密钥明文落库、口令泄漏）**不可事后补救**。故 v1.1 新增本章，并把 S 系列正式纳入编号体系。
>
> **排序规则**：**安全类一律优先于性能类**（详见表与理由见 §1 的排序规则框）。本章内按 S-id 顺序（P0 在前）。
>
> **核实说明**：以下每一条都在代码中实地核对过，并标注了**与评审意见不一致之处**（S-5 的一部分实际已完成、B-20 不应自行设计参数）——请以代码为准。

### 9.1 S-1 [P0] 前台 JWT 签名密钥有硬编码默认值 → 任何人可伪造前台身份

**证据**（[PublicAuthService.java:33-39](../backend/src/main/java/com/unicorn/studio/service/PublicAuthService.java#L33-L39)）：

```java
public PublicAuthService(PublicUserMapper userMapper,
                         PasswordEncoder passwordEncoder,
                         @Value("${app.public.jwt-secret:public-dev-secret-please-override-0123456789}") String secret) {
    ...
    this.key = Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));   // 直接当签名密钥用，无任何长度校验
}
```

**两个叠加的事实，使这不是「一个宽松的默认值」而是一个可利用漏洞**：

1. **`application.yml` 里根本没有 `app.public.jwt-secret` 这一项**（已通读确认——文件里有 `app.admin.jwt-secret`，**没有** `app.public.*`）。所以除非运维**恰好**设置了环境变量 `APP_PUBLIC_JWT_SECRET`，这个属性**永远解析不到值**，永远落到 `@Value` 里的**字面量**。
2. 该字面量**随源码提交进了 git**，任何读过本仓库的人都知道它。

**利用方式（无需任何前置条件）**：拿这个已知密钥，用 HS256 签一个 `sub=<任意用户 id>` 的 token，即可冒充**任意已注册前台用户**——以他人身份发表评论、绕过 `parentId` 归属、绕过游客限制。

**为什么它比看起来更严重**：

- 前台 token **无 `status` 校验**：[`resolveFromHeader`](../backend/src/main/java/com/unicorn/studio/service/PublicAuthService.java#L80-L91) 只验签名与过期，**不查 `status`**。而后台侧是查的（[JwtAuthFilter.java:53-54](../backend/src/main/java/com/unicorn/studio/admin/security/JwtAuthFilter.java#L53-L54)）。后果：**被禁言的用户（`status=0`）拿着旧 token 继续发评论**——`login` 里那道 `status` 检查（[:71-73](../backend/src/main/java/com/unicorn/studio/service/PublicAuthService.java#L71-L73)）只挡住了「重新登录」，挡不住「继续用旧 token」。
- 前台 token **无吊销能力**：无 `jti`、无服务端存储（对比后台有 `RefreshTokenStore`），有效期 **7 天**（[:27](../backend/src/main/java/com/unicorn/studio/service/PublicAuthService.java#L27)）。**一旦密钥泄漏，已签发的伪造 token 在 7 天内无法作废**。
- **同一项目里后台侧做对了**：[JwtService.java:33-36](../backend/src/main/java/com/unicorn/studio/admin/security/JwtService.java#L33-L36) 在密钥为空或短于 32 字符时**直接拒绝启动**。前台侧没有对齐——这个不对称本身就说明它是疏漏而非有意设计。

**修法**（三步，缺一不可）：

```java
// ① yml 声明配置项，去掉源码里的默认值
// app.public.jwt-secret: ${PUBLIC_JWT_SECRET:}

// ② 构造函数里照抄 JwtService 的启动守卫
if (secret == null || secret.length() < 32) {
    log.error("PUBLIC_JWT_SECRET 未配置或长度不足 32 字符，拒绝启动（安全要求）");
    throw new IllegalStateException("PUBLIC_JWT_SECRET 未配置或长度不足 32 字符");
}

// ③ resolveFromHeader 补 status 校验（与 login 对齐）
PublicUser user = userMapper.selectById(Long.valueOf(claims.getSubject()));
if (user == null || user.getStatus() == null || user.getStatus() == 0) {
    return null;      // 与 JwtAuthFilter 同口径：不设置身份
}
```

> **⚠️ 必须轮换密钥，光改代码不够**：该字面量已进 git 历史，**任何在此期间读过仓库的人都能伪造 token**，而伪造的 token 在日志里与正常登录**不可区分**。因此上线该修复的同时必须**生成新密钥并替换**，让所有旧 token（含伪造的）一次失效。这也是本章反复强调「安全项不可事后补救」的原因。
>
> **吊销能力的补充建议**：前台 token 有效期 7 天偏长。若要支持「封禁即失效」，最小成本方案是在 token 里加 `jti` + 在 Redis 维护一个封禁名单（封禁时写入 `jti`，`resolveFromHeader` 命中即拒），或直接把有效期缩到 24h 并配合续期。**此项可与 S-1 的修复分开排期，但需登记为已知风险。**

### 9.2 S-2 [P0] `CryptoService` 密钥缺失时静默降级为明文存储

**证据**（[CryptoService.java:53-65](../backend/src/main/java/com/unicorn/studio/common/crypto/CryptoService.java#L53-L65)、[:75-77](../backend/src/main/java/com/unicorn/studio/common/crypto/CryptoService.java#L75-L77)）：

```java
String material = firstNonBlank(cryptoSecret, jwtSecret);
if (material == null || material.length() < 16) {
    this.keySpec = null;
    this.plainFallback = true;                                  // ← fail-open
    log.warn("...敏感配置将【明文存储】...");                      // ← 仅告警，不阻断
}
...
public String encrypt(String plainText) {
    ...
    if (plainFallback) {
        return plainText;                                       // ← 原样返回明文
    }
```

**⚠️ 两种部署情形必须分开看，结论不同**（v1.2 修订：v1.1 把两种情形混写在一段里，读者容易误读为「默认部署 = 明文落库」——实际**生产的表现是「密钥复用」，不是明文**）：

`application.yml:118` 是 `secret: ${APP_CRYPTO_SECRET:}`，`:121` 是 `jwt-secret: ${ADMIN_JWT_SECRET:}`，**两者默认都为空**。而 `CryptoService` 的取值逻辑是 `firstNonBlank(cryptoSecret, jwtSecret)`（[:55](../backend/src/main/java/com/unicorn/studio/common/crypto/CryptoService.java#L55)）：

| 情形 | 前置条件 | `firstNonBlank` 结果 | **实际后果** |
|---|---|---|---|
| **① 生产** | **必须**配了 `ADMIN_JWT_SECRET`——否则 [`JwtService:33-36`](../backend/src/main/java/com/unicorn/studio/admin/security/JwtService.java#L33-L36) 会**直接拒绝启动**，服务根本起不来 | 退到 `ADMIN_JWT_SECRET` | **密钥复用**（**不是明文**）：用**后台 JWT 签名密钥派生**出 AES 加密密钥。见下方 ① |
| **② 本地开发** | 两个都没配（开发机常态） | `null` → `plainFallback = true` | **明文落库/明文出库**。见下方 ② |

**① 生产：密钥复用（机密性与完整性未分离）**

「签发后台会话」与「加密落库密钥」**共用同一份秘密材料**。两者本应隔离——一个是**完整性**用途（HMAC 签名），一个是**机密性**用途（AES 加密）。后果：

- JWT 密钥一旦泄漏，**历史密文随之可解**（攻击者已具备的全部条件）；
- 该 secret 常在多环境/多服务间复用，复用面即爆炸半径；
- 轮换其中任何一个都会**同时打断另一个**（换 JWT 密钥 → 历史密文全废；换加密密钥 → 全体后台会话失效），运维上互相绑架。

**② 本地开发：明文存储**

`plainFallback = true` 时 `encrypt()` **原样返回明文**（[:75-77](../backend/src/main/java/com/unicorn/studio/common/crypto/CryptoService.java#L75-L77)）。若开发库被导出、或**开发环境填的是真实 key**（很常见，因为要联调真模型），即等同于泄漏。启动时有一条 WARN，但告警不是控制。

> **定级依据**：**① 比 ② 更严重**——② 影响的是开发机（可补救、爆炸半径小），而 ① 影响生产，且把两套密钥体系的安全边界绑成了一个。

**修法**：

```java
// 生产 fail-closed：不满足条件直接拒绝启动，与 JwtService 统一
if (material == null || material.length() < 32) {
    if (!allowPlaintext) {                       // allowPlaintext 来自显式开关，默认 false
        throw new IllegalStateException("APP_CRYPTO_SECRET 未配置或长度不足 32 字符，拒绝启动（安全要求）");
    }
    ... // 仅当显式开启 app.crypto.allow-plaintext=true 时才允许降级（本地开发用）
}
// 且不再回退到 jwt-secret：机密性与完整性密钥必须分离
```

> **运维后果必须写进文档**：更换 `APP_CRYPTO_SECRET` 会让**已存储的密文无法解密**（[application.yml:117](../backend/src/main/resources/application.yml#L117) 已注明）。因此这项修复的落地步骤是：**先在后台重新填写 API Key → 再切换密钥**，或提供一次性重加密脚本。

**③ 注释与实现不符（勘误）**：[CryptoService.java:26](../backend/src/main/java/com/unicorn/studio/common/crypto/CryptoService.java#L26) 的类注释写「（PBKDF2 式简单派生）」，但 [`deriveKey`](../backend/src/main/java/com/unicorn/studio/common/crypto/CryptoService.java#L155-L166) 实际是**单轮 SHA-256**：

```java
byte[] digest = MessageDigest.getInstance("SHA-256").digest(material.getBytes(UTF_8));  // 单轮，无盐、无迭代
```

**这不是 PBKDF2**，注释必须改。至于要不要**真的**换成 PBKDF2/Argon2，取决于 `APP_CRYPTO_SECRET` 的性质：

- 若它是**≥32 字符的随机串**（设计意图），单轮 SHA-256 **足够**——高熵输入不需要 KDF 拉伸，注释改掉即可；
- 若允许运维填**人类可记的口令**，则单轮 SHA-256 面对离线爆破**很弱**，必须换 PBKDF2/Argon2 并加盐。

> **建议**：按前者处理（改注释 + 在 yml 注释里明确要求「随机串，非口令」），并在 S-2 的启动守卫里顺带校验熵下限（如要求含大小写+数字）。另注意长度阈值不统一：`CryptoService` 用 `< 16`，`JwtService` 用 `< 32`，文档说「≥32 字符」——**统一为 32**。

### 9.3 S-4 [P0] Redis 口令（及数据库口令）以默认值形式进入 git 历史

**证据**（[application.yml:63-72](../backend/src/main/resources/application.yml#L63-L72)、[:31-36](../backend/src/main/resources/application.yml#L31-L36)）：

```yaml
redis:
  host: ${REDIS_HOST:<<REDACTED-公网IP已更换>>}        # ← 真实公网 IP 写进仓库
  password: ${REDIS_PASSWORD:<<REDACTED-真实口令已轮换>>}     # ← 真实口令写进仓库
datasource:
  password: ${DB_PASSWORD:123456}           # ← 弱口令默认值（注释已自认「开源前请移除」）
```

**问题的三类，按严重度**（v1.2 修订：v1.1 标题写「三个问题」但实际只列了两类——主机暴露与口令泄漏被混为一谈，**遗漏了「端口开放」这一独立维度**。网络可达性由「安全组是否放行 6379」决定，与「口令是否泄漏」是两件必须分别核实的事）：

**① Redis 实例的暴露面（独立维度：主机 + 端口）**

`host: ${REDIS_HOST:<<REDACTED-公网IP已更换>>}` 是一个**真实的公网 IP**。**公网可达性取决于两个独立条件**，必须分别核实：

| 核实项 | 说明 |
|---|---|
| 该 IP 是否为本机/内网地址的误写 | 先确认它确实是那台 Redis 的公网入口 |
| **安全组/防火墙是否放行 6379** | ← **v1.1 遗漏的维度**。Redis 只要端口对公网开放，即使有 `requirepass` 也已是高风险暴露面（0day/未授权访问/暴力破解） |
| Redis 是否绑定 `0.0.0.0` | `bind` 配置；应绑 `127.0.0.1` 或内网网卡 |
| 是否启用了 `protected-mode` | 与 bind 组合决定暴露面 |

**② 凭据泄漏**：Redis 与 MySQL 的口令默认值都是**真实凭据**，不是 `changeme` 这类占位符——`<<REDACTED-真实口令已轮换>>` 明显是个人口令。**它已经进入 git 历史**，`git log -p` 即可取出。

**③ 数据库弱口令**：`${DB_PASSWORD:123456}`——若生产未设 `DB_PASSWORD`，则用的是弱口令。

> ⚠️ **① 与 ② 叠加才是最坏情形**：一台**公网可达**（①）且**口令已公开**（②）的 Redis——可被任意读写全部缓存、限流计数、刷新令牌。
>
> **本方案不代为连接探测**，请由负责人从运维侧核实全部四项。**这是 S-4 里唯一建议不等文档修完就立刻处理的事项**——因为 `<<REDACTED-公网IP已更换>>` + `<<REDACTED-真实口令已轮换>>` 是一对**可直接连接的真实凭据**，而里面存着刷新令牌、权限缓存与限流计数。

**修法**：

- **立即轮换**：Redis `requirepass` 换新口令；若曾用过默认值，**数据库口令同样轮换**（该路径下 `DB_PASSWORD` 默认值可能已在生产生效）；
- **收紧网络暴露面**：安全组仅放行内网、Redis 改绑内网网卡或 `127.0.0.1`、确认 `protected-mode` 已启用、禁止公网直连 6379；
- 把 yml 的默认值改为**空**（`${REDIS_PASSWORD:}`、`${DB_PASSWORD:}`、`${REDIS_HOST:}`），并在启动时校验非空——与 `JwtService` 的 fail-closed 风格统一；
- **git 历史重写是可选项，轮换是必选项**——即便重写了历史，凭据也应视为已泄漏（可能已被 fork/克隆/缓存）。

### 9.4 S-3 [P1] AI「测试连通性」的 `apiUrl` 未做校验 → 服务端请求伪造（SSRF）

**证据链**（三处叠加，缺一不成问题）：

1. [`AiConfigService.test(form)`](../backend/src/main/java/com/unicorn/studio/AIWorker/service/AiConfigService.java#L130-L147) 优先采用**请求体里的表单值**（设计意图是「先测再存」）；
2. [`AiRuntimeConfig.normalizedBaseUrl()`](../backend/src/main/java/com/unicorn/studio/AIWorker/config/AiRuntimeConfig.java#L61-L77) 只做**路径规整**（去尾斜杠、裁掉 `/chat/completions`），**不校验协议，也不校验主机**——`http://` 放行，任意主机放行；
3. 该 URL 被交给 `OpenAiApi.Builder().baseUrl(...)`，由**服务端**发起 HTTP 请求（[ChatClientFactory.java:68-92](../backend/src/main/java/com/unicorn/studio/AIWorker/service/ChatClientFactory.java#L68-L92)）。

**利用者是需要 `ai:test` 权限的管理员**（[AiConfigController.java:77-79](../backend/src/main/java/com/unicorn/studio/AIWorker/controller/AiConfigController.java#L77-L79)）——**不是匿名**，这降低了定级，但**不消除风险**，因为后果包含**密钥外泄**：

| 后果 | 说明 |
|---|---|
| **API Key 外泄** | 探测请求会带着 **apiKey 作为 Bearer 头**发往指定地址。因此一个只有 `ai:test`（而无完整 key 读取权——GET 只返回脱敏值，见 [AiConfigController.java:47-51](../backend/src/main/java/com/unicorn/studio/AIWorker/controller/AiConfigController.java#L47-L51)）的管理员，可以把 `apiUrl` 指向自己的服务器，**从库中取出明文 Key 并外带** |
| 内网探测 | 可探测内网服务与端口（错误信息会经 `humanizeError` 返回给调用者） |
| 云元数据 | 可请求 `http://169.254.169.254/...`（AWS/阿里云等的实例凭据端点） |
| 明文传输 | 允许 `http://`，Key 在链路上明文 |

**修法**（在校验层做，不要散落在调用点）：

```java
/** 校验探测/保存的 apiUrl：仅 https + 拒绝私网/环回/链路本地/元数据地址段 */
public static void validateApiUrl(String url) {
    URI u = URI.create(url.trim());
    if (!"https".equalsIgnoreCase(u.getScheme())) throw ...;   // 如允许 http，须显式开关
    String host = u.getHost();
    // ① 拒绝字面量私网/环回/链路本地（含 IPv6 ::1 / fc00::/7 / fe80::/10）
    // ② 域名必须解析后校验解析结果（防 DNS rebinding）
    InetAddress addr = InetAddress.getByName(host);
    if (addr.isLoopbackAddress() || addr.isSiteLocalAddress()
            || addr.isLinkLocalAddress() || addr.isAnyLocalAddress()
            || isUniqueLocalV6(addr)) throw ...;
    // ③ 建议叠加厂商域名白名单（openai.com / bigmodel.cn / deepseek.com ...）
}
```

> **注意 DNS rebinding**：只在「校验时」解析一次域名是不够的——攻击者可以让域名先解析到公网 IP（通过校验），连接时再解析到内网 IP。**严格的做法是校验解析结果并在连接时复用同一 IP**（或直接采用**域名白名单**，这也是本场景最实用的方案：AI 提供商就那么几家）。
>
> **落点**：`AiConfigService.test()` 的探测路径**与**`save()` 的保存路径**都要校验**——否则可以「先存一个内网地址，再触发对话」。保存路径当前同样没有校验。

### 9.5 S-5 [P1] `/api/ai/chat` 无认证，匿名可消耗真实 API 额度

3. **收紧前的必要前提**：见 S-7——只要 `X-Forwarded-For` 仍可伪造，**任何 IP 维度限流都是无效的**，仅靠调小 5 次/分解决不了问题。

### 9.6 S-7 [P1] `X-Forwarded-For` 被无条件信任 → 全部 IP 限流可被绕过（v1.1 新发现）

> **本条不在原评审意见内，是本次核查中发现的**。它的影响面**超出 AI 接口**，直接击穿 §2「已达标项」里那条「限流 Lua 原子 `INCR+EXPIRE`」所承诺的保护，故独立编号。

**证据**（[IpUtils.java:11-18](../backend/src/main/java/com/unicorn/studio/common/IpUtils.java#L11-L18)）：

```java
String forwarded = request.getHeader("X-Forwarded-For");
if (forwarded != null && !forwarded.isBlank()) {
    int comma = forwarded.indexOf(',');
    return (comma > 0 ? forwarded.substring(0, comma) : forwarded).trim();   // ← 取第一个 = 客户端可伪造的那个
}
return request.getRemoteAddr();
```

**关键在于代理的行为**。有**两条**代理路径，且**两条都会让伪造值直达后端**：

**路径 A（生产，nginx）——追加语义**：

```nginx
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;   # ← 追加，不是覆写
```

攻击者自行发送 `X-Forwarded-For: 1.2.3.4`，到后端时该头变为 `1.2.3.4, <真实客户端IP>`——而代码取的是**第一个**，**恰是攻击者可控的那个**。

**路径 B（开发/前端服务，Node 代理）——原样透传**：

[frontend/server/index.js](../frontend/server/index.js) 的 `proxyToBackend` 是

```js
const headers = { ...req.headers, host: targetUrl.host }   // 原样透传全部客户端头，且不追加 XFF
```

即**客户端的 `X-Forwarded-For` 原封不动到达后端**——连「该取第几个」都不必考虑，**直接命中**。这条路径**比 nginx 场景更容易复现**（前端服务是开发默认入口），也进一步说明「取第一个值」在两种代理下都是错的。

**后果：全部 8 个 IP 限流维度形同虚设**，每次请求换一个伪造 IP 即可无限调用：

> **⚠️ 定级前提（v1.2 补充，证据链完整性所需）**：本条**以「请求经代理到达后端」为前提**。当前部署下该前提成立但**外网不能直连**——[application.yml:3](../backend/src/main/resources/application.yml#L3) 的 `server.address: 127.0.0.1` 让应用**只监听回环**：
>
> | 拓扑 | 攻击者能否从公网利用 | 说明 |
> |---|---|---|
> | 经 nginx / Node 代理暴露（**当前**） | ✅ 能 | 伪造头随代理抵达后端，即表中效果 |
> | 直连 8080 | ❌ 不能（需已在本机） | 但本机上的低权限进程/其它服务仍可利用 |
>
> **加这条限定的原因**：不加会让读者以为「现在就能从公网无限爆破后台登录」，从而**高估紧迫性**。
>
> ### ⚠️ 更正（v1.2）：**账号锁定不受本缺陷影响**，故严重性低于「无限爆破」
>
> 撰写本节时曾断言「`LoginLockService` 的锁定计数同样按 IP，一并失效」——**这是错的**，经核实已更正：
>
> [LoginLockService.java:14-15](../backend/src/main/java/com/unicorn/studio/admin/security/LoginLockService.java#L14-L15) 的类注释明确写着「状态存 `sys_user`（数据库持久化，重启/多实例不丢），**与 IP 级内存限流独立生效**」；实现上 `onFailure`（[:35-45](../backend/src/main/java/com/unicorn/studio/admin/security/LoginLockService.java#L35-L45)）按 **`user.getId()`** 累加 `failed_login_attempts`，达 5 次则写 `locked_until`。
>
> **即：锁定是「按账号」的，与 IP 完全无关**——伪造 XFF 也绕不过它。
>
> | 攻击场景 | 是否被 XFF 缺陷放大 |
> |---|---|
> | 针对**某一个**管理员账号爆破口令 | ❌ **不放大**——5 次后锁 30 分钟（每账号每小时上限 10 次），这是有效防线 |
> | **撞库 / 密码喷洒**（每个账号试少量口令，横向扫很多账号） | ✅ **被放大**——锁定是「每账号」的，而 IP 限流失效后，攻击者可对 **N 个账号各试 5 次**且不受总速约束。这才是本缺陷在登录侧的真实风险 |
> | 其余 7 个维度（注册/评论/留言/PV/AI） | ✅ 全部被放大（见下表） |
>
> **因此 S-7 的正确定位**：它**不是**「后台可被无限爆破」（那有账号锁定兜底），而是**「整套 IP 维度限流承诺失效 + 登录侧防护被削去一层（防撞库）」**。定级仍为 P1，但理由应与上表一致，不应夸张。

| 被击穿的限流 | 阈值 | 实际效果 |
|---|---|---|
| **后台登录** | 5 次/分 | → 无限次。**注意**：账号锁定（5 次/账号/30 分钟）**仍然有效**，故不是「单账号可无限爆破」，而是**防撞库/密码喷洒的一层被削去** |
| 前台登录 | 10 次/分 | → 无限次 |
| 注册 | 10 次/时 | → 无限次（可批量注册） |
| 评论 / 游客评论 | 10 次/分 / 10 次/时 | → 无限次 |
| 留言 / PV 埋点 | 5 次/时 / 60 次/分 | → 无限次（**PV 数据可被刷**） |
| AI 对话 | 5 次/分 | → 无限次（**真实费用失控**，见 S-5） |

**同一缺陷的第二处**：[AccessLogFilter.java:91-97](../backend/src/main/java/com/unicorn/studio/common/log/AccessLogFilter.java#L91-L97) 用 `forwarded.split(",")[0]` 取 IP ——**审计日志里记录的客户端 IP 同样可伪造**，削弱了追溯能力（审计留痕的价值一半在于 IP）。

**修法**：

1. **明确信任边界并落到配置**（二选一）：
   - **应用只经可信代理暴露** → 让代理**覆写**该头（`proxy_set_header X-Forwarded-For $remote_addr;`）或改用专用头 `X-Real-IP`；后端**从右往左**取第 N 跳（N = 可信代理数量）；
   - **应用可能被直连** → **完全不信任** `X-Forwarded-For`，只用 `request.getRemoteAddr()`。
2. 把「可信代理跳数」做成**显式配置**（如 `app.security.trusted-proxy-count`，默认 `0` = 不信任任何 XFF）——业界标准做法，也是**最小改动**：

```java
/** trustedProxyCount=0 时完全不信任 XFF（安全默认值） */
public static String getClientIp(HttpServletRequest request, int trustedProxyCount) {
    String remote = request.getRemoteAddr();
    if (trustedProxyCount <= 0) return remote;
    String xff = request.getHeader("X-Forwarded-For");
    if (xff == null || xff.isBlank()) return remote;
    String[] hops = xff.split(",");
    int idx = hops.length - trustedProxyCount;          // 从右往左取
    return idx >= 0 ? hops[idx].trim() : remote;
}
```

3. **`AccessLogFilter` 与 `IpUtils` 共用同一实现**，避免两处口径不一致。

> **前提说明**：[application.yml:3](../backend/src/main/resources/application.yml#L3) 的 `server.address: 127.0.0.1` 让应用**只监听回环**——这是很好的基础，意味着**默认部署下应用无法被直连**（真正的客户端 IP 来自代理）。所以修复方向是**第 1 条的「从右往左取」**，而不是简单丢弃 XFF。但如果生产是「直接暴露 8080 + 前面挂 CDN」之类的拓扑，则 **XFF 完全不可信**，必须按 `trustedProxyCount=0` 处理。**请先确认生产拓扑再改**。

### 9.7 S-8 [P1] 文档类上传无内容校验（随 B-17 处理）

**现状**（[FileService.java:37-45,70-75](../backend/src/main/java/com/unicorn/studio/admin/service/FileService.java#L37-L45)）：图片走魔数 + `ImageIO` 重解码、视频走容器魔数，**文档类附件（pdf/zip/doc/docx/xls/xlsx/ppt/pptx/txt/md）只校验扩展名与大小**，内容完全未验证。

**先明确哪些风险**不**存在**（避免过度设计）：

- 扩展名白名单**很紧**：`html` / `svg` / `js` / `jsp` **都不在允许列表**内，且存储文件名是 **UUID** 而非原名（[:104-105](../backend/src/main/java/com/unicorn/studio/admin/service/FileService.java#L104-L105)）——因此**路径穿越**与**通过扩展名直接触发的存储型 XSS** 都不成立。这一点设计得对。
- `.zip` 虽被允许，但服务端**从不解压**，所以**压缩炸弹不成立**（只是占存储）。

**残留的真实风险**：

1. **本站成为任意内容的托管点**：任何字节都可以 `.pdf` 之名存到 `/uploads/...` 并由本站域名提供访问——可用于分发恶意文件/钓鱼（借用可信域名的信誉）。这是「内容校验」要解决的核心问题。
2. **缺少 `X-Content-Type-Options: nosniff`**：后端未设置该响应头（已 grep 确认，`WebMvcConfig` 的静态资源映射与全局都没有）。虽然 `Content-Type` 由扩展名决定、且扩展名白名单很紧，但 `nosniff` 是这类「用户上传内容由本站域名提供」场景的**标准兜底**。顺带一提，前端的 Node 服务**已经设置**了安全响应头（见《前端主站优化方案》），**后端这条路径没有**——**两条serving路径的安全基线不一致**，值得统一。
3. **无 `Content-Disposition`**：对新窗口打开的文档类附件，建议 `attachment` 以避免浏览器内联渲染未知内容。

**修法**：文档类补魔数校验（pdf `%PDF-`、zip 及 OOXML 系列的 `PK\x03\x04`、旧版 Office 的 OLE 头 `D0 CF 11 E0`），`txt`/`md` 因无固定魔数可限定「必须是可打印文本 + 长度上限」；并在静态资源响应上补 `X-Content-Type-Options: nosniff`。

### 9.8 S-6 [P1] actuator 的暴露面（详见 B-19）

已在 [B-19](#b-19-p1-无-actuator指标改动前后无量化基线) 展开，此处仅登记要点：**`/actuator/heapdump` 导出的整个堆中驻留着 `AiRuntimeConfig` 里已解密的明文 API Key**（该类注释自述「持有的是已解密的明文 apiKey，仅存在于服务端内存」）以及 Redis/DB 口令。因此 actuator 必须：独立管理端口、独立默认拒绝的过滤器链、生产不暴露 `heapdump`/`env`/`configprops`，需要堆转储时走 `jcmd` 离线获取。

### 9.9 安全项小结与实施顺序

| 编号 | 级别 | 一句话 | 利用门槛 | 可否事后补救 |
|---|---|---|---|---|
| S-1 | P0 | 前台 JWT 密钥硬编码 → 伪造身份 | **读过仓库即可** | ❌ 必须轮换密钥 |
| S-2 | P0 | 加密密钥缺失则明文存储 | 默认部署即触发 | ⚠️ 需重加密已存数据 |
| S-4 | P0 | Redis/DB 口令进 git 历史 | 读过仓库即可 | ❌ 必须轮换凭据 |
| S-7 | P1 | **XFF 可伪造 → 全部 8 个 IP 限流被绕过**（账号锁定仍有效，故登录侧风险为「防撞库被削去一层」） | **一次请求即可** | ✅ 可修 |
| S-3 | P1 | AI 测试接口 SSRF + 可外带 Key | 需 `ai:test` 权限 | ✅ 可修 |
| S-5 | P1 | AI 对话匿名可调用 | 一次请求即可 | ✅ 可修 |

| S-6 | P1 | actuator 堆转储泄漏明文密钥 | 取决于暴露面 | ⚠️ 泄漏后同样要轮换 |

**建议的实施顺序**（同级内按「利用门槛」从低到高）：

1. **S-1** → 改配置 + 启动守卫 + `status` 校验，**并轮换 `PUBLIC_JWT_SECRET`**；
2. **S-4** → 清空口令默认值 + **轮换 Redis/DB 凭据** + 核实 Redis 网络暴露面；
3. **S-2** → 加密密钥 fail-closed（注意先重填 API Key 再换密钥）+ 修注释 + 长度阈值统一为 32；
4. **S-7** → 落地 `trustedProxyCount`（默认 0 的安全默认值）并统一 `IpUtils`/`AccessLogFilter`，**改前先确认生产拓扑**；
5. **S-3** → `apiUrl` 白名单校验（探测 + 保存两条路径都要）；
6. **S-5** → 对话接口加身份要求 + 全局日预算（**依赖 S-1 完成**）；
